## CL-D44 — Cross-operation input shapes are declared and checked
**Clauses:** CL-D44-autofix, CL-D44-map, CL-D44-readme, CL-D44-tests

*Decision ID:* CL-D44
*Kind:* fail-closed request-validation boundary
*Target and revision:* `tetsuh/pi-tidd-agents#74` at its initial body, which carries the observed reproducer from the authoritative Issue #36 comment, and the owner's live instruction `#74 を進めて`, with the six-point enumeration approved by the owner in the authoritative pull-request comment <https://github.com/tetsuh/pi-tidd-agents/pull/76#issuecomment-5442524616>
*Question:* How should the packaged CLI treat a cross-operation field that receives a structurally similar but wrong shape — the complete envelope, an operation's `data`, or a nested receipt?
*Options and trade-offs:* Option A leaves presence checking in place, which is the state that produced the reported failure. Option B accepts every plausible shape and normalizes internally, which never errors but makes the documented contract unknowable and hides a real mistake. Option C declares one shape per field and rejects the others at the boundary. A is silent and misleading; B trades a late wrong answer for no answer at all; C costs one classification helper and one section.
*Recommendation:* Option C, with the declaration published beside the field in the invocation map.
*Owner choice:* Option C, as six explicit choices. One: the five declared fields — `operator_revalidate.captured`, `workspace_verify.expected`, `workspace_cleanup.receipt`, `fingerprint_snapshot.snapshot`, and `gate_result_validate.result` — are the complete CL-D44 set, pinned exactly by regression. Two: each declared shape is judged by one predicate; a supplied value is rejected because it fails the declared field's predicate, never because of what it was recognized to be, and no total classification of arbitrary objects is part of the contract. Three: `snapshot` requires the full producer shape, because `fingerprint_snapshot` hashes any object silently and nothing downstream would fail. Four: `result` is only a separating probe, after which the closed CL-D36 schema remains the sole semantic validator of gate results. Five: an object constructed by hand to satisfy a declared predicate passes; detecting fabricated producer output is outside this boundary. Six: declaring another field, changing a predicate's depth, or accepting a second shape for any field requires a new owner decision. `envelope`, `data`, and `receipt` remain distinct input shapes decided by structure rather than by what a caller names them; the map names each field's shape beside the field; a wrong shape stops with `input_shape_mismatch` before the operation runs, naming the field, the declared shape, and what arrived; the packaged CLI accepts no tolerant alternative for a declared field, and direct helper calls retain their base-compatible argument and output semantics.
*Rationale:* `operator_revalidate` reads `captured.data.identity`, so the packaged CLI request requires the complete envelope, while the CLI previously validated only that the field was present. Passing `operator_capture.data` — the plausible object — therefore crossed the boundary and failed later as `capture_failed: complete target identity is required`, an error naming the target rather than the request. That is the observed failure on `tetsuh/sitos#165`: a fresh exact-autofix run stopped before any gate or mutation with 0 gate invocations, 0 pushes, and no repository or GitHub mutation. Fail-closed behaved correctly; the diagnosis pointed at the wrong thing, and because exact autofix never resumes, an incidental composition slip discards a whole run on an unmoved target. Two neighbouring fields showed the same class from the other side: `workspace_cleanup` silently accepted three shapes for one field, and `fingerprint_snapshot` is total over objects, so an envelope supplied there produces a well-formed digest over the wrong bytes rather than an error at all. The correction is limited to the packaged CLI boundary: reject wrong shapes before dispatch while preserving direct helper compatibility and operation semantics. This decision adds no recovery, no normalization, and no tolerance at that boundary, and CL-D39 still governs recoverability for the keys it already names. CL-D42 is complementary and does not overlap: it labels what a value *is* inside the evidence envelope, while this decision declares what shape a *request field* takes. The predicate formulation is itself review-derived: the initial implementation classified every supplied object against an enumeration of known shapes, and successive review rounds each constructed an object falling between two classes, because a total classifier makes an unbounded claim any boundary object can falsify. One predicate per field makes the claim finite — each predicate is held to its producer by an executed positive composition fixture and to its neighbours by swap fixtures — and the diagnostic wording in the error message is explicitly not part of the accept/reject decision, so its looseness is not a defect. What the boundary does not do is stated rather than implied: an object constructed by hand to satisfy a declared predicate passes, exactly as CL-D42 does not detect a hand-retyped value.
*Validity and invalidation conditions:* Applies to the packaged CLI request boundary for the declared fields. It grants no authority, consumes no counter, changes no operation's semantics or output, and weakens no fail-closed, no-retry, no-resume, mutation, or publication boundary. Adding a cross-operation field without declaring its shape, declaring a field beyond the five recorded here, changing a predicate's depth, accepting a second shape for any field, or normalizing a wrong shape instead of rejecting it requires a new owner decision. If `operator_revalidate` ever stops reading the complete envelope, or `workspace_cleanup` ever needs a shape other than the receipt, the declarations recorded here are invalidated and must be re-derived from the consumers rather than adjusted in place. CL-D68 later declared `build_gate_launch.expectation` under its own decision. CL-D70 later let the one declared envelope field accept its producer payload, normalized to the envelope before any check.
