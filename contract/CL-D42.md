## CL-D42 — Evidence travels in one versioned envelope with labelled domains
**Clauses:** CL-D42-autofix, CL-D42-helper, CL-D42-readme, CL-D42-tests

*Decision ID:* CL-D42
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#36` at the current Issue #36 body and the owner's live instruction `go ahead`, scoped to exact PR `autofix`
*Question:* How can gate evidence be bound to the target it was captured from, when the parent supplies both sides of every comparison and the six CL-D9 values are indistinguishable by shape?
*Options and trade-offs:* Option A leaves each value bare and relies on the parent placing it correctly, which is the current state and is undetectable when it fails. Option B adds a second source of truth to compare against, which does not exist and would itself be parent-supplied. Option C makes each value self-describing inside one closed versioned envelope and adds a read-only verifier. A is free and silent; B is unavailable; C costs one helper and one section and detects the copy path but not a hand-retyped value.
*Recommendation:* Option C, scoped to exact PR `autofix`, with the residual stated rather than implied.
*Owner choice:* Option C. Gate evidence travels in one envelope carrying `schemaVersion`, capture identity, seven fingerprints, both capture brackets, and completeness, with every section closed. An unknown or absent version fails closed before any field is read. Under version 1 each fingerprint operation emits its own `{ domain, encoding, value }` record and assembly carries it unchanged; `domain` must equal its field. `raw_bytes`, `normalized_text`, and `canonical_json` are distinct byte domains with fixed fields and shapes. Packaged `evidence_verify` is read-only and repeatable. It compares all seven domains and every identity field — repository, number, base OID, head OID, base branch, head repository, head branch, state, and draft — against the expected target, requires both brackets to witness that identity, and rejects a moved bracket, incomplete pagination or completeness metadata, and head/base fingerprints inconsistent with the claimed identity. Lifecycle and branch identity are required: exact autofix cannot act on an unobserved state, draft flag, or head branch. This deliberately narrower envelope carries identity, fingerprints, brackets, and completeness, not Issue #36's review-evidence collections — check runs with app/source identity, commit statuses, reviews/threads, comments, or annotations. Those collections and the authoritative comment's cross-operation composition typing are deferred; Issue #36 stays open.
*Rationale:* The parent assembles the gate payload and also assembles the expectation it is checked against, so a misplaced value is self-consistent and passes every existing check: `gate_result_validate` compares `requiredEvidence` with `evidenceRead`, and both come from the parent. Before CL-D42, the three OID operations returned their OID and the digest operations returned a bare 64-hex string, so no value recorded which domain produced it. CL-D39 already recorded this as reachable and its recovery table already carries a row for a digest computed from the wrong domain, which is a documented remedy for a failure nothing detects; the outcome it protects against is a gate reviewing evidence from a different head and returning `MERGE`, which is the one result the closed loop exists to prevent. The operation-owned label carries the value's provenance, so the mix-up is caught without a second source of truth. The bound is exact: it defeats a labelled record copied from the wrong operation, and a value retyped by hand into a well-formed record stays undetectable here, which is why the operation declaring a domain remains its only source. Scope is exact PR `autofix` because that is where six same-shaped values are assembled together; the Issue root carries one specification fingerprint with nothing to confuse it with, and widening the surface without a demonstrated hole was rejected. The section fits under the existing baseline: the six files measure 115,874 bytes, so no ceiling raise is taken.
*Validity and invalidation conditions:* Applies to exact PR `autofix` and to the four sections the envelope actually carries. It certifies nothing about evidence it does not carry: an envelope that verifies proves identity, domain labelling, fingerprint equality, bracket stability, and completeness, and proves nothing about the review-evidence collections or about how one operation's output was composed into another's input. The verifier grants no verdict, no mutation authority, and no recovery beyond the keys CL-D39 already names; its failure is terminal under the deterministic action order. It adds no shared-layer authority and changes no Issue or PR review-only behaviour. Adding, removing, or re-encoding a domain, accepting a second schema version, or relying on the envelope to detect a hand-retyped value requires a new owner decision. If a fingerprint operation ever stops being the sole source of its domain's value, the provenance basis recorded here is invalidated.
