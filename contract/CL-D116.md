## CL-D116 — The parent writes the autofix correction subject; the driver checks it against the commit convention
**Clauses:** CL-D116-record, CL-D116-driver, CL-D116-writer, CL-D116-skill

*Decision ID:* CL-D116
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#281`, before B4b of #249, under the owner's decisions (https://github.com/tetsuh/pi-tidd-agents/issues/281#issuecomment-6127207592, with the alarm revised in https://github.com/tetsuh/pi-tidd-agents/issues/281#issuecomment-6146666131)
*Question:* The exact-autofix writer committed every correction batch as `fix: <finding ids> (#<issue>)` with a prose `Test provenance:` paragraph (CL-D96). On tetsuh/hekatus PR #125 a gate raised `ADV-125-COMMIT-SCOPE`, because that repository requires `<type>(<scope>): <imperative summary> (#<issue>)` and a bullet-only body, and only a history rewrite cleared it. Who writes the correction commit's message, and how does a batch avoid a commit the gates will reject?
*Options and trade-offs:* (1) The parent writes the subject and the driver checks its shape: the message is still fixed before the writer launches, at one more parent step. (2) The writer passes the subject to `batch`: it knows the change best, but the message is no longer fixed at launch. (3) The type and scope come from configuration: hekatus uses several of each, so one configured scope is wrong there, and the summary still needs an author.
*Recommendation:* Option 1.
*Owner choice:* Option 1. A gate result with a correctable finding, its paths authorized, no longer launches the writer: the driver saves `MESSAGE_PENDING` and prints a `MESSAGE:` line naming `autofix.js message --run-dir <dir> --subject <subject>`, a convention line, and one bullet per correction, each folded to one line, control, format and separator characters included, so no gate text starts a line the parent reads as a dispatch line (#224); the commit body's bullets are folded the same way. The parent writes the subject `<type>(<scope>): <imperative summary>` and runs that command; only that command is taken while the subject is pending. The driver checks the subject, then launches the writer as before, its recheck and snapshot check included. The message is the subject, ` (#<issue>)`, a blank line, one bullet per correction, and one bullet naming the validation the batch runs before its commit; there is no prose paragraph, as #166 asks of a commit body, and `message_verify` still compares the commit with it. A refused subject prints `MESSAGE:` again with the reason; the third refusal stops `BLOCKED` with `commit_subject_refused`, before any writer launch or commit. With no convention configured the parent still writes the summary, so no subject is only finding ids.

The convention is the whole `commit` object of `.tidd.json` at the base commit, else that of the operator configuration, never merged, so a base file without the key never shadows the operator's; it is never read from the head. The validation commands keep CL-D97's order. When the key is not in the file the commands came from (a base file without it, or `--validate`), the operator configuration is read for the key alone: a file there without `validate` supplies it, and a file the reader refuses (CL-D97: unreadable, over 64 KiB, not BOM-free UTF-8, inside the checkout, not JSON) or that is not a JSON object stops the run, where a base `.tidd.json` or `--validate` used to skip the operator configuration. A base `.tidd.json` must still carry `validate`. The keys are `types` and `scopes` (nonempty lists of words of lowercase letters, digits and `._/-`), `scope` (`required` or `optional`) and `maxLength` (30 to 200, counting ` (#<issue>)`); none is required and no other is accepted. A malformed key stops the run `BLOCKED` at start, before the workspace is created. With no key, the types are the commitlint conventional list (build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test), the scope is optional and the length is unbounded; the convention line names the source, or `default`. The check takes one line of printable text, `<type>(<scope>)!: <summary>` with the scope and `!` optional, the type and scope from their lists, a summary that ends without a period, carries no `(#<n>)` reference and names no finding id of the batch, and the length. Imperative mood is the gates' to judge; nothing else is checked. The aggregate driver alarm rises from 110,000 to 120,000 bytes, the files measuring 115,460 on this change; the per-file alarm stays at 30,000.
*Rationale:* The parent can read the corrections and the convention, and the message stays one the driver fixed before the writer ran. A gate that rejects a commit's shape costs a push and a rewrite; the check costs one parent step.
*Validity and invalidation conditions:* Applies to the exact-autofix correction commit. Review-only runs commit nothing, and `review.js` still skips the operator configuration under `--validate`. A repository whose convention the four keys cannot state needs a new record. hekatus meets the convention only once its configuration carries the key, for example `"commit": {"scope": "required", "scopes": ["bench", "measurements"]}`.
