## CL-D112 — The clause pins of the helper map move to the code and the records
**Clauses:** CL-D112-record, CL-D112-markers, CL-D112-forward, CL-D112-tests

*Decision ID:* CL-D112
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#270`, pull request B1 of #249, under the owner's option (a) (https://github.com/tetsuh/pi-tidd-agents/issues/249#issuecomment-6105220135) and the corrected order (https://github.com/tetsuh/pi-tidd-agents/issues/249#issuecomment-6105250786)
*Question:* Since CL-D111 no run reads `references/helper-map.md` as guidance; both drivers still hash it into `contractInput` until the last pull request of #249 deletes it. Twenty-three clause pins across twenty-one records name the file, and eight tests assert its text as the statement of a rule. Where do those pins go, so that the deletion changes no pin?
*Options and trade-offs:* Option A repoints each pin to where the rule lives now: an invocation-map row's operation and inputs to the packaged CLI's operation table in `helpers/cli.js` and to the driver call site that runs it at the phase the row names; a constraint a row states beside its fields to the helper code that enforces it; a prose rule to the code comment or message that states it, else to the record's own sentence. Option B moves every pinned sentence into its record, which keeps prose as the pinned statement of rules the code implements and pushes CL-D45 and CL-D89 against the record limit. Option C deletes the pins with the file, which leaves the rules unpinned.
*Recommendation:* Option A.
*Owner choice:* Option A, as the corrected order already states. A clause whose anchors fall in more than one file is split into one clause per file, each carrying its record's marker; a file that lacked the marker gains one comment naming the records newly pinned to it. Four sentences were about the map document itself and are retired, with the record saying so: CL-D83-map ("This reference is read with `references/autofix.md`"), CL-D44-autofix's "the map names the shape each field expects" (CL-D44 states it), CL-D68-map's "The installed package's own map governs a run" (restated in CL-D68 as a rule about the CLI), and CL-D86-map's "no retry beyond the CL-D39 recovery defined above" (a pointer into the file; CL-D86's recompose-once sentence is pinned instead). Rows that no driver runs (`marker_create`, `marker_reconcile`, `workspace_cleanup`) are pinned to the operation table and the enforcing code alone. The rule-stating tests assert the code or record instead; the tests about the file's existence, size, split, authority measurement and `contractInput` keep their reads of the map until the deletion (Issue #110's derived clause set names the split CL-D62 clauses). The file is byte-identical and the drivers read it into `contractInput` as before.
*Rationale:* The code is the one specification since CL-D111; a pin on it fails when the implementation changes, which a pin on prose no run reads as guidance cannot. One file per pull request keeps each change's record evidence small.
*Validity and invalidation conditions:* Applies to the clause pins and tests that named `references/helper-map.md`. It changes no rule, grant or boundary: every requirement the map stated is either pinned to the code that enforces it, stated in its record, or retired as a sentence about the document. The three other mode references, the deletion, `AUTHORITY_FILES`, both `CONTRACT_INPUT_FILES`, the guards and the ceiling are the later pull requests of #249. The autofix driver does not recompose a refused post-push revalidation (CL-D86); that gap is recorded here, not closed. Reviving a pin on a deleted file, or moving a rule out of its record without a code anchor, requires a new owner decision. Three of those retired sentences, CL-D44-autofix's, CL-D68-map's and CL-D86-map's, stayed asserted through the file by `test/issue-74-composition-shapes.test.js`, `test/issue-111-gate-read-launch.test.js` and `test/issue-34-bounded-recovery.test.js` until CL-D118 repointed CL-D68-map's to CL-D68 and dropped the other two. #249 later deleted the map (CL-D119); neither driver hashes it into `contractInput`.
