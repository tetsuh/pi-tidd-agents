## CL-D49 — A successful cleanup result is the terminal workspace evidence
**Clauses:** CL-D49-autofix, CL-D49-tests

*Decision ID:* CL-D49
*Kind:* fail-closed terminal-evidence boundary
*Target and revision:* `tetsuh/pi-tidd-agents#80` at its initial body and the owner's live instruction to proceed with #80 first
*Question:* After a successful `workspace_cleanup`, which observation is the terminal workspace evidence, and may the run still verify the removed path?
*Options and trade-offs:* Leaving the question unstated is the observed state: the orchestrator verified the removed path, Git returned `ENOENT`, and a successful cleanup became a dead run. Adding a recovery for that failure would weaken the fail-closed rule for a case that is simply a caller error. Naming the cleanup result terminal and forbidding later workspace calls on the removed path costs one sentence and removes the class.
*Recommendation:* Name the cleanup result terminal, forbid post-removal workspace operations, and keep the terminal recheck operator-side.
*Owner choice:* As recommended. A successful `workspace_cleanup` result is the terminal workspace evidence — it carries the removed path and the terminal head and tree — so no `workspace_*` operation may target the removed path afterwards, and the terminal recheck after removal is operator-side only. A post-removal verification failure is a caller error, never evidence about the target.
*Rationale:* Observed on `tetsuh/sitometron` autofix runs: roughly ninety logged entries of the class `ENOENT during workspace_verify post-removal confirmation; the run is not resumable`, with gates 0/15, pushes 0/5, and a clean operator checkout — runs that had completed their work and then destroyed the result by verifying a path they had just removed. Nothing in the packaged operations changes here, because nothing needed to: `cleanupWorkspace` already returns `removed`, the path, and the terminal head and tree, and a regression pins that it still does, so the prose is checkable rather than aspirational. The helper-side guard Issue #80 floated — classifying `workspace_verify` on a path named in a presented cleanup receipt — is declined: `workspace_verify` receives no receipt, so recognizing one would require declaring a new cross-operation field, which the CL-D44 freeze reserves for a new owner decision, and the prose alone removes the class without widening any surface.
*Validity and invalidation conditions:* Applies to exact PR `autofix` after a successful cleanup. It grants no recovery, retry, resume, or compensation, and does not weaken cleanup's own identity checks or its fail-closed failure behaviour; a cleanup that fails remains `BLOCKED` exactly as before. If `workspace_cleanup` ever stops returning the removed path and terminal head and tree, the basis for calling its result terminal is invalidated.
