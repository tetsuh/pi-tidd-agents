## CL-D99 — The correction push carries a lease on the head it was built on
**Clauses:** CL-D99-record, CL-D99-forward, CL-D99-tests

*Decision ID:* CL-D99
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#207` at its body and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/207 (comment of 2026-10-03)
*Question:* `push_publish` pushed with a plain non-force `git push`, and its comment said a remote that moved refuses the push. That holds only for a remote that moved forward or sideways: a branch rewound to an ancestor of the batch's head turns the push into a fast-forward, which succeeds and restores the commits someone removed. How does the push refuse every moved remote?
*Options and trade-offs:* Option 1 adds `--force-with-lease=refs/heads/<branch>:<parent>`, so Git itself refuses the push unless the remote branch is exactly the head the batch built on; the check and the update are one step, but the flag is force-named, against the contract's "non-force push" wording. Option 2 reads the remote with `git ls-remote` just before pushing and stops on a difference; nothing is force-named, but a change between the read and the push is not caught.
*Recommendation:* Option 1.
*Owner choice:* Option 1. The push carries exactly one `--force-with-lease=refs/heads/<branch>:<parent>`, where `<parent>` is the new commit's sole parent, which must be the head the batch built on: the captured public head, or for a later batch of the run the public head it built on, always passed as `parent`, which must descend from the captured head; `push_publish` refuses a HEAD that is not exactly one commit on it. HEAD is resolved once, and the push sends that resolved commit, never `HEAD` read again, so a HEAD moved before the push is not what lands. Git skips the lease for a ref already up to date and exits 0, so the push's porcelain status decides: anything but one fast-forward of that commit onto the branch is refused. CL-D30's exactly normal non-force `HEAD:refs/heads/<verified-pr-branch>` push, as `CONTRACT.md`, `references/autofix.md`, and the README state it, is carried out by `push_publish` as this push: the commit `HEAD` resolved to, under the one lease. The lease never overwrites: it is narrower than the plain push, which it replaces, and the run's "one non-force push" means this push. `--force`, a `+` refspec, and any other force-named flag stay forbidden.
*Rationale:* The bounded batch publishes exactly one commit on exactly the head it was reviewed against. A lease states that bound to Git, which enforces it atomically; a read before the push states it to the driver, which cannot.
*Validity and invalidation conditions:* Applies to `push_publish`'s one push. Any other force-named flag, a lease on another ref or value, or a push without the lease requires a new owner decision.
