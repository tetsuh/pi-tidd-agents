## CL-D89 — The writer commits and pushes through packaged operations with the operator identity
**Clauses:** CL-D89-map, CL-D89-capture, CL-D89-operations, CL-D89-record, CL-D89-tests, CL-D89-boundary

*Decision ID:* CL-D89
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#181` at its body and the owner choices https://github.com/tetsuh/pi-tidd-agents/issues/181#issuecomment-5816104411, https://github.com/tetsuh/pi-tidd-agents/issues/181#issuecomment-5822980178, and https://github.com/tetsuh/pi-tidd-agents/issues/181#issuecomment-5823139754 (working session of 2026-09-25)
*Question:* Exact-autofix attempt 8 on PR #178 reached the writer, passed every guard and all 984 tests, and failed at the one normal commit with `Author identity unknown`: every Git command runs under isolated config, and isolated config carries no `user.name` or `user.email`. The push has the same gap, because the isolation empties `credential.helper` and replaces `HOME`, so the operator's `gh auth git-credential` helper never runs. Earlier runs pushed (PR #149) only because their writer ran Git outside the isolation. Where do the commit identity and the push credential come from, and who composes the two commands?
*Options and trade-offs:* For the identity, Option A reads the operator checkout's effective `user.name` and `user.email` once at preflight, records them, and passes exactly those two to the commit; Option B ships a fixed bot identity as a setting; Option C lets the commit read the operator's global config, which reopens the hooks, signing, and templates the isolation keeps out. For the commands, packaged operations the writer invokes make the isolation and the two additions deterministic but cross CL-D37's structural boundary for two operations; leaving the writer to compose `git commit` and `git push` with documented `-c` flags keeps CL-D37 intact but keeps the writer-composed step that failed attempt 8 and reads the operator's global config.
*Recommendation:* Option A for the identity; the packaged operations, with the push naming exactly one credential helper, `gh auth git-credential`.
*Owner choice:* Option A for the identity (https://github.com/tetsuh/pi-tidd-agents/issues/181#issuecomment-5816104411); the push under the same isolation with exactly one named helper (https://github.com/tetsuh/pi-tidd-agents/issues/181#issuecomment-5822980178); and the packaged operations, superseding CL-D37's "no commit, push" clause for exactly `commit_create` and `push_publish` (https://github.com/tetsuh/pi-tidd-agents/issues/181#issuecomment-5823139754). `operator_capture` records `commitIdentity` `{ name, email }` from the operator checkout's own configuration, the one read that is not isolated, and refuses a missing one (`commit_identity_missing`) or one Git would rewrite or split (`commit_identity_invalid`: an angle bracket, NUL, or line break anywhere, or at either edge one of the characters Git strips there, space and controls and `, : ; < > " \ '`) at preflight, before any gate. `commit_create` takes `created`, `captured`, and `message`: it runs in `created.path`, passes the captured identity by configuration and by the identity variables so no ambient value can replace it, stores the message as UTF-8 whatever the repository declares, takes the message on stdin as real bytes, refuses an empty index or message, and returns the commit and its sole parent. `push_publish` takes `created` and `captured`: it requires a successful `operator_capture` envelope and a `HEAD` that descends from the captured public head, checks every push URL Git would use (the workspace's own `origin`, rewrites applied; there must be exactly one), which must equal the captured and the recorded workspace URL, refuses one that is neither https nor a local path (an SSH remote would be reached with the operator's own keys, not the named helper) and an https URL that carries a username or password (those would authenticate instead of the helper), pushes `HEAD` to `refs/heads/<headBranch>` of the captured target and nothing beside it (no tags, submodules, or signing, whatever the configuration says, and immediately before the push it repeats preflight's unsafe-key check and refuses any `http.*` key, the remote's mirror, remote-helper, or proxy setting, or push options, because configuration can change after preflight and TLS, resolution, proxy, and header settings decide which peer receives the credential), never with force, clears the inherited helper list, names `gh auth git-credential`, and points gh at the operator's own configuration directory on every platform. Every Git command also drops `GIT_CONFIG`, `GIT_NAMESPACE`, and the TLS and HTTP transport variables from its environment. The proxy variables stay (https://github.com/tetsuh/pi-tidd-agents/issues/181#issuecomment-5841643694): an https push tunnels through a proxy with `CONNECT` and verifies TLS end to end, so the proxy cannot read the credential, and removing them would make the push impossible where GitHub is reachable only through one. Only the writer invokes them, and CL-D30's one commit and one non-force push per batch are unchanged. The packaged-helper alarm resets from 280,000 to 290,000 bytes (https://github.com/tetsuh/pi-tidd-agents/issues/181#issuecomment-5834493756): the pre-push review corrections put the helpers at 280,749, and nothing is compressed to fit, as CL-D37 asks. Merge, reply, approval, thread resolution, durable state, and scheduling stay outside the helpers, as CL-D37 says.
*Rationale:* The isolation was right and the run still ended at the commit, because the contract named no source for the two things isolation removes and the commit and push need. Naming them once, in the package, is the seventh member of the class that began with CL-D56: each ended with the composed request removed rather than the rule restated. gh is the authentication the run already uses for snapshots and replies, so naming it grants nothing new; a fixed bot identity would have added a setting for a fact the checkout already holds.
*Validity and invalidation conditions:* Applies to `operator_capture`'s identity, `commit_create`, `push_publish`, and the writer's commit and push steps. The isolation of every other Git command, the guards around the commit and push, `message_verify`, and the post-push revalidation are unchanged. A capture forged to satisfy the envelope shape is outside this boundary, as CL-D44 already states for every declared field. Reading the identity from anything but the operator checkout's configuration, inferring or normalizing one, naming a second credential helper, admitting an SSH or other non-https remote, adding force in any form, or letting anything but the writer invoke either operation requires a new owner decision. CL-D99 later made the one push carry a lease on the head the batch built on, the only force-named flag it may use, and send the commit `HEAD` resolved to once rather than `HEAD` read again.
