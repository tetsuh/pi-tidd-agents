## CL-D50 — The CL-D30 addendum is a third disclosure stage
**Clauses:** CL-D50-base, CL-D50-tests

*Decision ID:* CL-D50
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#87` at its remaining acceptance criteria, under owner decision `DEC-PR88-SCOPE-001` choice B, and the owner's live instruction to proceed
*Question:* Where should the CL-D30 addendum live, given that nearly every new decision lands in it, the disclosure guard left `autofix.md` 1,714 bytes, and the PR Skill's mode invariant says exactly one mode reference is read?
*Options and trade-offs:* Leaving the addendum inside `autofix.md` keeps one file per mode but leaves decision-sized additions unable to fit the file where they land. Making the addendum a second mode reference contradicts the mode invariant and the CL-D6 grammar, which recognize two modes, not three. Making it a third disclosure stage — Skill, then the selected mode reference, then the addendum only when the exact `autofix` token selected the mode — relocates the growing prose without adding a mode, without rewording anything, and without touching the invariant's subject: the addendum is not a mode reference; it is selected by one.
*Recommendation:* The third disclosure stage.
*Owner choice:* As recommended. The addendum moves whole into `references/autofix-addendum.md`, byte-for-byte; no prose is reworded. `autofix.md` ends by directing the stage: the exact `autofix` token additionally selects the addendum, read only then and after the base reference. The mode-dispatch invariant is unchanged — exactly one mode reference is read, and review-only runs read nothing new. The aggregate set becomes seven files with its total and ceiling unchanged, the pre-split disclosure guard keeps bounding what every autofix run reads first (Skill plus base), and the addendum stage carries the 28,000-byte guard its section already had.
*Rationale:* CL-D43 named the split as the structural answer and CL-D48 recorded the measured reason: decisions land in the addendum, and the file they landed in had 1,714 bytes of disclosure headroom while the aggregate had thousands. Splitting by mode would have multiplied modes; splitting by disclosure stage matches how the prose is actually read — the addendum was already conditionally selected by the exact token inside `autofix.md`, so the stage boundary existed in prose before it existed on disk. Relocation is verified, not asserted: the manifest's addendum-scoped clauses moved with their sections, the split CL-D27 pins were preserved inside existing addendum clauses, and the stage guards are asserted per stage. Two map rows gained a `(CL-D45)` annotation because the marker moved out with the addendum and the clause anchored on it; that is the only textual addition beyond the directing sentence. Where guard comments and test names stated the six-file count as live fact they now say the aggregate; CL-D43 and CL-D48 keep saying six because they measured six when they were decided.
*Validity and invalidation conditions:* Applies to the PR authority layout. No prose meaning changes, no mode is added, and no guard is weakened: the aggregate ceiling, the disclosure guard, and the addendum guard all continue to assert. Splitting the addendum further, adding a fourth stage, or moving content between stages requires a new owner decision. If the addendum stage ever stops being selected exclusively by the exact `autofix` token, the basis for keeping it outside the always-read base is invalidated.
