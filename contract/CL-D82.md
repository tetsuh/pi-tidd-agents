## CL-D82 — The gate launch names the workspace its child runs in
**Clauses:** CL-D82-map, CL-D82-addendum, CL-D82-record, CL-D82-tests

*Decision ID:* CL-D82
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#159` at its body and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/159#issuecomment-5748464962 (working session of 2026-09-20)
*Question:* `references/autofix.md` and the addendum state that the gates run at the isolated workspace's cwd, and `build_gate_launch` emitted no `cwd`: pi-subagents resolves an absent `cwd` from the caller's context (`params.cwd ?? ctx.cwd`), which during a run is the operator checkout at the immutable baseline. After the writer commits a correction the two trees differ, so a route-to-Sol gate would read the uncorrected tree. Is the builder wrong, or the sentence?
*Options and trade-offs:* Option A narrows the two sentences to say that gates run in the operator checkout, which costs no code but writes the hazard into the contract: a gate would judge a correction it cannot see. Option B gives the builder the created workspace and emits its path, which closes the hazard for exact autofix and leaves review-only, where no workspace exists, exactly as it was; it costs one optional input, one declared shape, and the screen CL-D81 already applies to a workspace path. Option C requires a `cwd` in every mode, which would make review-only derive one from its capture — a second input shape for no gain, since review-only reviews the checkout it already runs in.
*Recommendation:* Option B.
*Owner choice:* Option B. `build_gate_launch` takes `created`, the data of `workspace_create` already declared as a CL-D44 cross-operation field, and emits `cwd` at that workspace. The envelope states the mode, so the builder relates the two rather than leaving the relation to the parent: an `autofix` launch without the workspace is refused, and a `review-only` launch carrying one is refused, each at phase `build`. Review-only therefore emits the request it always emitted, with no `cwd` (CL-D91 later replaced every mode's inline task with a pointer to the payload file). The workspace must be the linked one — a clone fallback is retained and never entered — and its path is screened for a NUL byte, a lone surrogate, and a relative spelling exactly as CL-D81 screens the writer's. Those three screens are the whole of it, and what the builder judges is structure: CL-D44 states that an object constructed by hand to satisfy a declared predicate passes, so a fabricated workspace and a path carrying any other control character are accepted here and refused, if at all, by the operation that uses them. Nothing else in the launch changes, and the gates' authority, evidence, and verdict vocabulary are untouched.
*Rationale:* Both sentences were true of the writer and of validation and false of the gates, and the gap was invisible because the receiver silently supplies a cwd of its own. Emitting the workspace makes the statement true where it was written rather than deleting a guarantee the run needs: after a correction, the tree a gate judges is the tree the run made.
*Validity and invalidation conditions:* Applies to `build_gate_launch` in exact autofix. The request review-only emits is unchanged apart from CL-D91's later pointer, though its builder now refuses a workspace it must not take and, like CL-D81's, any field it does not know; the grant, every guard, and every other launch are untouched. The regression drives the installed pi-subagents over the built request, as CL-D81's does, and dropping that check requires a new owner decision. Requiring the workspace, supplying a cwd in review-only, or accepting a workspace the builder does not screen requires a new owner decision. If a pi-subagents release stops resolving an absent `cwd` from the caller's context, this record's hazard disappears but its rule stands until restated.
