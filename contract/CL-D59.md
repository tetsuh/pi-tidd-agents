## CL-D59 — Agent identities name workflow roles; models are deployment configuration
**Clauses:** CL-D59-resolution, CL-D59-tests

*Decision ID:* CL-D59
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#100` at the design proposal https://github.com/tetsuh/pi-tidd-agents/issues/100#issuecomment-5509747293 and the owner decision https://github.com/tetsuh/pi-tidd-agents/issues/100#issuecomment-5509800274
*Question:* Should the closed loop's agent identities describe stable workflow responsibilities, with provider, model, and thinking level held in deployment configuration, and what happens to the six packaged model-derived agent files?
*Options and trade-offs:* Option A renames the four workflow agents to `tidd-adversarial-reviewer`, `tidd-drift-reviewer`, `tidd-safety-reviewer`, and `tidd-autofix-worker`, keeps each old name as a transitional alias for one release, removes the two workers no workflow references, and leaves gate identities inside the envelope to a second decision. Option B keeps model-derived names and documents overrides against them, which leaves every model replacement looking like a contract change and keeps model families in durable gate records. Option C renames and migrates gate identities in one change, which couples a prose rename to a validator change and makes one large review of two independent risks.
*Recommendation:* Option A.
*Owner choice:* Option A. Two pull requests, roles first; the validator accepts v1 for one release under the second decision; `glm-worker` and `terra-worker` are removed so the package ships exactly the four roles; the v2 fresh-finding prefixes will be `ADV-`, `DRIFT-`, and `SAFETY-`. Each role file carries its old name in `aliases`, its unchanged default `model`, `thinking`, and `tools`, and a description that names the responsibility, not the model. This decision widens the CL-D1 `agents/` freeze exactly once more, for these renames, the description and alias changes, one body sentence that asserted a model, and the two removals; it is not a standing permission.
*Rationale:* A role name that encodes a model makes every model retirement look like a workflow change, and on 2026-09-02 a GitHub-injected check failed for exactly that reason when its model was withdrawn. pi-subagents already separates the two: `aliases` resolve explicit `agent` inputs to the canonical name, and a unique exact configured name resolves before any alias is consulted (`resolveAgentName` in agents.ts; the collision error exists only for runtime-registered agents). An old file left beside the aliased role would therefore not collide: a leftover legacy definition would silently bypass the role for that old name, which is why the old files are replaced rather than duplicated. Overrides are looked up by the canonical name only (`overrides[agent.name]` in agents.ts), so an override keyed by an old name does not apply merely because that string remains an alias; the README says so rather than leaving it to be rediscovered. The two removed workers were referenced by no skill or prompt, and CL-D3's exclusion rationale for them stands as history. The adversarial and safety reviewer roles remain read-only and fresh-context, the drift reviewer role remains read-only in the forked context its decision-oracle function depends on (unchanged from `terra-oracle`; owner Option A on SOL-104-DRIFT-CONTEXT, https://github.com/tetsuh/pi-tidd-agents/issues/100#issuecomment-5524798954, which also amended the Issue's criterion 3), and the writer role remains the sole bounded writer; the preflight check now names the capability each role must resolve with, so a misconfigured override fails closed before a gate can begin.
*Validity and invalidation conditions:* Applies to both workflow roots' preflight and every prose reference to an agent. It changes no gate order, authority, confirmation duty, readiness outcome, or packaged operation; gate identities inside the envelope stay `sol` and `terra` until the second decision. A role name proves nothing about model independence; any later independence rule must compare the runtime-resolved provider and model. The aliases expire after one release by a recorded decision; adding an agent file, a role, or a tool requires a new owner decision.
