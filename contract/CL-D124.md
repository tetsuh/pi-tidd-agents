## CL-D124 — The version-2 Issue schema has no candidate field
**Clauses:** CL-D124-record, CL-D124-schema, CL-D124-skill, CL-D124-contract

*Decision ID:* CL-D124
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#312`, the schema change CL-D123 left separate, with the owner's choice in the working session (2026-10-20)
*Question:* #310 (CL-D123) retired the Issue candidate route, so the Issue root never sets `candidateIdentity`, yet gate-result schema version 2 still declared it on the Issue correlation and the Issue finding record, and the validator still compared it. CL-D120 requires an owner decision to change either root's shape. Should the field stay, unset, or go?
*Options and trade-offs:* Keeping it costs nothing at run time, but every Issue gate decodes a field no run fills, and the helper, the Skill and the gate contract describe a candidate that no longer exists. Removing it changes the Issue shape and the output schemas of the two roles that review the Issue root, and leaves version 1 as it is.
*Recommendation:* Remove it from version 2.
*Owner choice:* Version 2's Issue correlation and Issue finding record declare no `candidateIdentity`, so a version-2 Issue result or expectation that carries it is refused as an unknown field, and the validator compares no candidate. Version 1 keeps its rule: its Issue finding record still requires a candidate identity. `tidd-adversarial-reviewer` and `tidd-drift-reviewer` carry the new schema in their agent definitions (CL-D90). The version-2 pull-request finding record keeps its schema; its validator already refuses `candidateIdentity`.
*Rationale:* Since CL-D123 nothing sets the field, so removing it changes no accepted Issue result, and the Issue shape matches the route that remains.
*Validity and invalidation conditions:* Applies to gate-result schema version 2 on the Issue root and to the two Issue roles' output schemas. It changes no pull-request shape and no version 1 rule. Giving the Issue root a candidate again requires a new owner decision.
