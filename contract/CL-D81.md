## CL-D81 — The exact-autofix writer launch is composed by a packaged builder
**Clauses:** CL-D81-autofix, CL-D81-autofix-map, CL-D81-readme, CL-D81-record, CL-D81-tests

*Decision ID:* CL-D81
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#152` at its body, whose "Owner decision (2026-09-20)" section records the choice (working session of 2026-09-20)
*Question:* CL-D80 stated the writer launch's acceptance and time bound in prose and recorded that a builder is the answer if the parent composes another field wrongly. The parent then did: PR #149's first exact-autofix run carried `preflight`, which pi-subagents accepts only beside a workflow script, and the run ended before the writer wrote anything. Does the writer launch become a builder, and what proves the receiver accepts what a builder emits?
*Options and trade-offs:* Option A adds the newly broken field to the prose, the fourth repetition of a class the builder families already closed elsewhere (CL-D56, CL-D68, CL-D73); the parent keeps composing the request, so the next field is free to break in the same way. Option B packages the composition and proves the built request against the receiver's own validators; it costs a tenth builder operation, one more declared CL-D44 field, and a regression that reads the installed pi-subagents. A regression written against this package's own predicates would have caught neither failure: both requests were internally consistent, and the receiver refused them.
*Recommendation:* Option B.
*Owner choice:* Option B. `build_writer_launch` takes `created` — data of `workspace_create`, declared as a CL-D44 cross-operation field — and the `task` the parent decides, and emits the whole `tidd-autofix-worker` launch document the run sends, the receiver's own defaults apart: `agent: "tidd-autofix-worker"`, a role name and never a model, `task`, `cwd` at the created workspace, `context: "fork"`, `async: true`, `outputMode: "inline"`, and CL-D80's `acceptance: false`, `timeoutMs: 3600000`, and `checkpointBeforeDeadlineMs: 600000`. The parent states the task and nothing else: a request carrying any other field is refused at phase `build`, and a workspace that is not a linked one is refused there too. The built request goes to the subagent tool unchanged, as `build_gate_launch`'s does; nothing outside the builder may add a field to it, and no check enforces that, so it is stated where the parent reads it. The regression drives the installed pi-subagents' own validators over the built request — `normalizePublicSubagentExecution`, the `SubagentParams` schema, run over the document and not only read for the names it declares, and `validateAcceptanceInput` — through the packaged CLI as well as in process, and skips only where pi-subagents is not installed.
*Rationale:* Every hand-composed request in this flow has failed at least once, and each time a builder closed the class; the writer launch was the last one, and it failed twice in one day. Checking the built request against this package's predicates would repeat the mistake that let both failures through, so the check is the receiver's own code, read from the installation the run will use rather than a vendored copy that could drift from it.
*Validity and invalidation conditions:* Applies to the `tidd-autofix-worker` launch in exact autofix. It grants the writer nothing: the grant, the one-commit and one-push bounds, every guard, and every review-gate launch are unchanged, and the settings are CL-D80's. Changing a field the builder emits, accepting another input from the parent, or dropping the receiver-side check requires a new owner decision. If a pi-subagents release removes `false` as the acceptance shorthand, CL-D80's invalidation applies here and the builder must be restated. CL-D94 later gave every gate launch the same `timeoutMs` under its own decision, with no checkpoint request.
