## CL-D100 — External review is best effort
**Clauses:** CL-D100-record, CL-D100-prose, CL-D100-autofix-prose, CL-D100-driver, CL-D100-phases, CL-D100-forward-d18, CL-D100-forward-d93, CL-D100-tests

*Decision ID:* CL-D100
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#226` at its body, which records the owner's decisions of 2026-10-04
*Question:* A round whose three gates return `MERGE` could still end `WAITING_EXTERNAL_REVIEW`: final readiness waited for an external review provider to finish, for a quiet period and an observation window, and for requirements only a human can settle. Whether a provider has finished is hard to decide from the outside, so the wait was unreliable in both directions. What does final readiness wait for?
*Options and trade-offs:* Option 1 keeps the waits and improves the detection of a finished provider; the outcome keeps depending on a third party's signals. Option 2 makes external review best effort: a finding that is present is answered, and nothing waits for one that may still come; a late finding is then found by the next run or by the human who merges.
*Recommendation:* Option 2.
*Owner choice:* Option 2 (https://github.com/tetsuh/pi-tidd-agents/issues/226). An external review provider's state is reported as observed and is never waited for and never a failure; the quiet period, the observation window, and their timing are gone, and the publication reports the latest external event and says that external review is not waited for. A finding that is present is answered as before: an unresolved review thread stops `WAITING_FOR_OWNER`, and a latest decisive `CHANGES_REQUESTED` review stops the run. A requirement only a human or GitHub settles never holds `MERGE_READY` back and is named in `operator_actions` of the run that ends `MERGE_READY`: a required approval, every ruleset and protection setting the workflow reads but does not evaluate (a check a ruleset requires included, since the ruleset is not evaluated), strict required checks, and a `mergeable_state` of `blocked`. Checks keep their rule: a pending or failed check run or commit status, and a check protection requires that has not reported, wait or block as before; a check run posted by the provider's app (the app CL-D92's classification reads), or the provider's commit status (the exact context and the creator that classification requires; any other spelling of the context, and the same context from any other creator, is an ordinary status; the newest status of a context whose `created_at` reads as a date decides, and a status whose `created_at` does not is judged as well), that no protection requires is reported with the provider's state, and one that protection requires keeps the rule of every required check; a requirement pinned to an app is that app's check run only, so another app's check run or a commit status of the same name is not required by it. A change of the snapshot, a provider's state included, still reruns the gates (CL-D93); only the wait is gone. Every other `mergeable_state` that is not mergeable (`behind`, `dirty`, `unknown`, `draft`) waits as before. A branch protection the workflow cannot read is settled by GitHub's own `mergeable_state` (owner decision UNREADABLE-PROTECTION-BY-MERGEABILITY, https://github.com/tetsuh/pi-tidd-agents/pull/227#issuecomment-5977640182): GitHub answers 404 for a branch without protection and for a token that may not read it alike, and the workflow does not tell them apart; while that protection holds the merge back GitHub reports `blocked`, which is named, or a state that waits, and a mergeable state means GitHub found every protection requirement met, so nothing is named. No policy state blocks any more: a policy the workflow reads but cannot evaluate, a ruleset's unreadable rules included, is named, and only a failed snapshot stops the run, so exact autofix no longer blocks on an ambiguous policy. The provider is the one the snapshot classifies, CodeRabbit; a check run or status of any other service is an ordinary check. `WAITING_EXTERNAL_REVIEW` stays the token for what still waits.
*Rationale:* The gates decide readiness; the workflow never merges, so it has nothing to wait for where only a human or GitHub can act. Waiting on a provider added an outcome the owner could not rely on and removed none of the provider's findings, which are still answered when present.
*Validity and invalidation conditions:* Applies to final readiness in both PR modes, on the driver and on the prose path. Waiting for a provider again, treating a provider's state as a failure, or holding `MERGE_READY` back for a requirement named above requires a new owner decision.
