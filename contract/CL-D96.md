## CL-D96 — The packaged autofix driver runs correction cycles; the writer's process commits and pushes
**Clauses:** CL-D96-driver, CL-D96-alarm-scope, CL-D96-record, CL-D96-tests

*Decision ID:* CL-D96
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#196` at its body and the owner choices https://github.com/tetsuh/pi-tidd-agents/issues/196#issuecomment-5870929892 and https://github.com/tetsuh/pi-tidd-agents/issues/191#issuecomment-5857263114 (working sessions of 2026-09-28), and the alarm reset https://github.com/tetsuh/pi-tidd-agents/issues/196#issuecomment-5909781641
*Question:* The #191 spike took PR #195 to `MERGE_READY` by exact autofix without rescue (milestone #155) with a driver outside the package. Does the package ship the autofix half, and who commits and pushes?
*Options and trade-offs:* Option A: the writer edits and then runs two driver commands, `pre-edit` and `batch`, so its own process runs `commit_create` and `push_publish` and CL-D89 stands. Option B: the driver commits and pushes after the writer returns, which needs CL-D89 superseded.
*Recommendation:* Option A.
*Owner choice:* Option A, packaged (the first two comments above; the third approves the alarm reset). `skills/closed-loop-pr/driver/autofix.js` sequences preflight (`operator_capture`, `writability`, `workspace_create`, validation from `.tidd.json` at the base), then per gate the target re-read, operator revalidation, workspace verification, the snapshot evidence, expectation, and launch with the workspace; on a correctable finding it composes the writer task and `build_writer_launch`. The writer's `pre-edit` runs `guard_before_edit`; its `batch` runs `overlay_freeze`, validation, two `overlay_compare`, staging exactly the overlay's paths, the manifest capture and an overlay-to-manifest path equality, the manifest compare, `commit_create`, `message_verify`, two `workspace_verify`, a recheck that the complete pull request target (head, base, head repository and branch, open, not draft) is still the one the batch built on and that the operator is unchanged, and `push_publish`, the first refusal ending the batch. After the push the driver verifies the public head, workspace, and operator (CL-D86), invalidates every earlier verdict, and restarts at convergence within its cap and at Sol beyond it. The mechanised judgments: `authorizedPaths` is the tracked paths the findings name, matched whole and longest first so the tail of a longer tracked or ambiguous name is never a name of its own, a name ending only at whitespace or listed punctuation so an unrecognised name waits for the owner (a basename counts when exactly one tracked file carries it), plus the pull request's changed files; the commit message is `fix: <finding ids> (#<issue>)` with one line per correction and a `Test provenance:` line naming the validation the batch runs before its commit (CL-D25); a finding is corrected when a formal gate raised it (`sourceKind` `gate`), it is criterion-anchored, Major or Minor, not out of scope, and proposed `fixed` or `deferred`, and every unresolved finding, assigned ones included, is classified on its current record before a writer launches; an assigned finding settles only when Sol confirms its fix, it still proposes `fixed`, and Sol links no counterexample to it, an earlier gate's confirmation routing it to Sol while it stays assigned; a CL-D85 recorded finding settles; any other finding stops `WAITING_FOR_OWNER`. Like review.js, the driver takes `--language-profile`, reports a validator that cannot run as `harness_failed`, stops `BLOCKED` when the workspace's ignored paths change after a validation (the batch refusing, before its validation, any ignored-path change the writer made), and names in the `MERGE_READY` reason only the gates that returned `MERGE` on the final head. A convergence role the role preflight found disabled (`--convergence disabled`) is skipped at start and at every restart, which then begin at Sol, and is reported disabled (CL-D62). Caps: convergence 5, Sol and Terra 15, pushes 5, the third time one assigned finding is reported unresolved. `writer-done` prints `WAIT` and changes nothing until the runner records the autofix worker's own run, named by its UUID and not an earlier batch's, run in the workspace and started after this writer launch, in a terminal state; an absent, unreadable, other run's, or other agent's record is not one. A fix a later gate reports unresolved again returns to the writer. Every stop rechecks the operator and removes the workspace unless `BLOCKED`, and a refused removal turns the stop `BLOCKED`; the workspace is created linked with no clone fallback, since a gate never enters a clone (CL-D82); the stop reports this run's retained workspace roots (a kept workspace, a refused or partial removal, or a refused creation) and their count in `operator_actions`, after any earlier action, and the drafted publication carries them with the temporary root as `{tmp}`, as it carries no local path (#221); a terminal recheck that fails turns the stop `BLOCKED` and keeps the workspace. Both drivers refuse a run directory or package path that is not a plain path (letters, digits, `_ . / -`), before creating anything, because the commands they print name both for a shell. `autofix.js` is the only driver file that names `commit_create` or `push_publish`. The writer's task, commit message, and completion judgment are `driver/writer.js`; it names no operation. The path matching and `authorizedPaths` are `driver/paths.js`; it names no operation. The autofix driver holds every obligation CL-D93 states for review-only through the same code, `driver/phases.js`, which both drivers call: the target bound before any run directory (a head in another repository refused there), the guard that ends every later failure with a token, the Issue re-read, Sol's trusted human comments, the recorded class (a deferred non-Blocker follow-up advances), the gate-result read (`WAIT` on a running gate; CL-D51's relaunch key as autofix.md states it, so only an absent or empty output is relaunched, once per run, never after a writer launch, with the target, operator, workspace, and fingerprints rechecked first, and malformed output stops `BLOCKED`), the snapshot evidence with new external evidence restarting the sequence at convergence within its cap and at Sol beyond it, before a later gate, a writer launch, and readiness, so no formal gate is skipped and no correction rests on a stale snapshot, the first gate refusing an issue, its comments, or the body changed after the run read them and a diff that is not valid UTF-8, the body and issue-spec revalidation before every gate (every head fingerprint too while the head is unchanged; the head-bound ones are rebound after each push, whose own checks CL-D86 states), and CL-D93's final policy. The per-file driver alarm stays at 30,000 bytes; the aggregate driver alarm resets from 60,000 to 100,000 bytes on the CL-D37 review recorded here, because the aggregate now covers seven files, sharing `phases.js` rather than copying it is the smaller of the two ways to hold those obligations, and the review-only corrections PR-A took after this change was first measured grew the shared code as well. CL-D97 later resets the aggregate to 105,000 bytes.
*Rationale:* The spike's last run needed no hand intervention; the earlier runs' driver defects were fixed in code, and packaging keeps those fixes where every consumer runs them.
*Validity and invalidation conditions:* Applies to the autofix driver and the writer's two commands. The helpers, the gates, CL-D89's writer-only commit and push, and the outcome tokens are unchanged. Letting the driver itself commit or push, widening the correctable class, or deriving `authorizedPaths` from anything but the findings and the changed files requires a new owner decision.
