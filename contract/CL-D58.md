## CL-D58 — The gate envelope is read from the structured output path, never from a notice
**Clauses:** CL-D58-transport, CL-D58-tests

*Decision ID:* CL-D58
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#86` at the measured correction https://github.com/tetsuh/pi-tidd-agents/issues/86#issuecomment-5509685542 and the owner's selection of **Option A** on the pull request that carries this record
*Question:* Where does the parent read the CL-D36 gate envelope, and what does CL-D51's "zero designated output bytes" observe, when the runner's completion notice for a single asynchronous run can read `(no output)` while the child's designated output file holds a complete envelope?
*Options and trade-offs:* Option A states the read path once in the shared transport section — the file at the run's structured output path, read after completion — binds CL-D51's dividing line to that file, and adds no helper code and no new operation. Option B additionally packages a `gate_result_read` operation that opens the path, which adds a filesystem read site under CL-D37 for a rule the parent can follow by reading one runner-reported path. Option C leaves the read path unspecified and treats the notice as authoritative, which is the observed failure: on PR #99 (2026-09-02) four Sol runs the parent declared dead had each written a complete envelope to that path, one of them a `MERGE`; the parent read the notice's `(no output)`, spent the CL-D51 relaunch on a run that had succeeded, and two findings were recovered only by hand from transcripts.
*Recommendation:* Option A.
*Owner choice:* Option A. The envelope is the file at the run's structured output path as reported by the runner's run status, read after completion. A completion notice, wait result, or preview is a courier and never the envelope; `(no output)` in one is transport indeterminacy, and the parent must read the path before classifying the run. Zero designated output bytes means that file is absent or empty after completion; an exit code, success flag, or runner status never substitutes for reading it. A validated envelope at that path is the verdict whatever the runner's status says. A validation failure at that path remains a tool failure governed by the owning workflow or selected mode's existing retry/fail-stop rule; this decision grants no retry change. Exact autofix's first-malformed-result terminal rule and CL-D51's zero-byte relaunch remain unchanged.
*Rationale:* CL-D51 chose zero output as the dividing line because the designated output file "either exists with bytes or it does not"; that observation is only as good as the place it is taken, and the prose never said where. A notice is a message about the run, not the run's output, so its silence carries no information about the target — the no-information principle Issue #86 asks for, at its sharpest, since here the information existed on disk and was discarded. Naming the file once in the shared section governs both workflow roots and every route, keeps CL-D51's rule intact by construction, and requires no new code: the runner already reports the path in its run status. The runner's omission of the envelope from a single-run notice is an upstream matter and is not something this package can repair; the package can only refuse to read a courier as the envelope. The `terminated` run whose file held a complete envelope shows why status never substitutes for the file in either direction.
*Validity and invalidation conditions:* Applies to every formal Sol and Terra invocation under CL-D36 in both workflow roots. It grants no new retry, no counter relief, no tolerance for a partial or malformed envelope, and no change to each owning workflow or selected mode's existing retry/fail-stop rule, including exact autofix's first-malformed-result terminal rule. CL-D51's single zero-byte relaunch and its preconditions remain unchanged. If the runner stops reporting a structured output path, or stops writing the envelope to a file, the read path recorded here is invalidated and CL-D51's dividing line with it. Packaging a read operation, or reading the envelope from anywhere else, requires a new owner decision.
