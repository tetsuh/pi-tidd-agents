## CL-D90 — The gate schema lives in the gate roles' agent definitions
**Clauses:** CL-D90-launch, CL-D90-read, CL-D90-record, CL-D90-tests

*Decision ID:* CL-D90
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#184` at its body and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/184#issuecomment-5845374102 (working session of 2026-09-26)
*Question:* Gate launches failed before any verdict because the `outputSchema` the parent passed to the subagent tool was not the packaged schema: re-typing the ~11 KB document as tool-call arguments displaced every `required` array into its object's `properties`, and the provider rejected it. It was intermittent, on a `gpt-5.6-luna` parent, in a consumer repository and here on PR #182. How does the schema reach the child without the parent transcribing it?
*Options and trade-offs:* Declaring the schema in the gate roles' agent definitions, which pi-subagents reads as the child's `outputSchema`, removes the transcription and lifts CL-D35's freeze on `agents/` for one addition. A pre-launch comparison would need the parent to hand over what it is about to send, which is the same transcription. Classifying the failure after the fact names it but prevents nothing.
*Recommendation:* The agent definitions, with the after-the-fact classification as a backstop.
*Owner choice:* Option 1 (https://github.com/tetsuh/pi-tidd-agents/issues/184#issuecomment-5845374102). `tidd-convergence-reviewer`, `tidd-adversarial-reviewer`, `tidd-safety-reviewer`, and `tidd-drift-reviewer` declare `outputSchema` in their frontmatter, equal to `gate-result.js`'s `SCHEMA` exactly and pinned by a test, so the schema has one source. `build_gate_expectation` returns only `expected` and `build_gate_launch` puts no `outputSchema` in the request, so no document the parent composes holds the schema, and the workflow prose of both roots no longer tells the parent to request one. Because a launch `outputSchema` overrides the agent definition's, `gate_result_read` reads the schema the child ran with from the step's recorded `structuredOutputSchemaPath`, only from inside the run directory by filesystem identity, compares it against `SCHEMA`, and refuses a difference as `schema_transcription_mismatch`, naming the first differing JSON path, whatever the step's status. For a complete step the check fails closed: an unrecorded schema is `designated_schema_unrecorded` and an unreadable one `designated_schema_unreadable`, so a replacement gate definition that declares no `outputSchema` cannot read on; an incomplete step without a schema reports as incomplete.
*Rationale:* "Pass the request unchanged" is not something a model can guarantee for a document that size, and the prose rule had already been broken by two parent models. The seventh member of the CL-D56 class ends like the others: the composed document leaves the parent's hands.
*Validity and invalidation conditions:* Applies to the four gate roles' definitions, `build_gate_launch`'s request, and `gate_result_read`. The schema itself, its validator, and every gate's authority are unchanged. A gate role invoked outside the closed loop now also returns the gate envelope. Declaring a schema that is not `SCHEMA` exactly, putting a schema back in the launch request, or reading a result whose child schema differs requires a new owner decision.
