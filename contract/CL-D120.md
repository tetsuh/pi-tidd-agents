## CL-D120 — Gate result schema version 2 carries an Issue correlation beside the pull-request one
**Clauses:** CL-D120-record, CL-D120-schema, CL-D120-envelope, CL-D120-read, CL-D120-skill, CL-D120-contract

*Decision ID:* CL-D120
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#190`, step 1 of the owner's route A (https://github.com/tetsuh/pi-tidd-agents/issues/190#issuecomment-6233941786)
*Question:* Version 2's gate result correlation names a pull request's base, head repository, head branch, head and draft on both roots, so an Issue gate result passes `gate_result_validate` only with invented values, and the Issue Skill names neither `build_gate_launch` nor `gate_result_validate`, which the shared gate contract requires. How does an Issue gate get a correlation of its own?
*Options and trade-offs:* A version 3 for both roots moves every pull-request envelope and fixture to a new version for one release. Filling the pull-request fields with Issue values keeps the schema but invents a branch, a draft and a head repository. A per-root branch inside version 2 leaves the pull-request shapes byte-identical and gives the Issue its own closed shapes.
*Recommendation:* The per-root branch inside version 2.
*Owner choice:* The per-root branch, as the #190 comment records. The Issue correlation is closed and carries `repository`, `number`, `lifecycle` (`open` or `closed`), `gate`, `invocation`, `contractInput`, `snapshotFingerprint` and `issueSpec`, with `candidateIdentity` present exactly while a candidate is under review. An Issue finding or confirmation binds to its gate by `issueSpec` in place of `headOid`, and an Issue finding record names the candidate identity exactly when the correlation does. The validator checks each envelope against its root's own closed schema and never walks a union. Each gate role's agent declares the schema of the roots its gate reviews (`ROLE_SCHEMAS`): the pull-request schema for `tidd-safety-reviewer`, unchanged; the Issue schema for `tidd-drift-reviewer`; and for `tidd-adversarial-reviewer` and `tidd-convergence-reviewer` a union whose correlation, findings and confirmations are each an `anyOf` of the two roots' shapes. `gate_result_read` accepts a child that ran with any one of those packaged schemas. An Issue volatile target names no pull-request field, and its `issue_spec` fingerprint must equal `issueSpec`. The Issue Skill states that its gates are composed and validated by the packaged helpers, and replaces its `tidd-issue-gate-v1:<run_nonce>:<attempt_seq>` launch identity with the packaged one: the per-gate `invocation`, the runner run id the launch returns, and the payload digest; the parent consumes each run id once and expires the earlier one at a relaunch. No packaged helper derives the Issue `contractInput` or `snapshotFingerprint`, so the parent supplies both until the Issue driver of step 2 does, and the per-file helper alarm resets from 30,000 to 32,000 bytes for every helper file, prompted by `helpers/launch.js` (both owner choices in the working session).
*Rationale:* The pull-request schema and every pull-request result keep their bytes and their behaviour, and an Issue result can be validated without a field the Issue does not have. Version 1 is unchanged and keeps the pull-request shape on both roots for its one release.
*Validity and invalidation conditions:* Applies to version 2 envelopes, the expectation builder, the gate launch's volatile target, `gate_result_read`'s schema check, the four gate roles' schemas, the Issue Skill's gate composition and launch identity, and the gate contract's correlation statement. It adds no driver and no snapshot. Each Issue finding copies `issueSpec`, and each Issue record copies `candidateIdentity`, as 64-hex values from the expectation, the same transcription class as the pull-request `headOid` and `observedHeadOid` (CL-D69). Deriving the Issue `contractInput` and `snapshotFingerprint`, moving CL-D31 candidate publication out of prose, or changing either root's shape requires a new owner decision. #304 later took `convergence` out of the Issue root's gates and gave `tidd-convergence-reviewer` the pull-request schema (CL-D121). #306 later derived both in the packaged Issue driver (CL-D122). #310 later retired the Issue candidate route (CL-D123): the Issue root never sets `candidateIdentity`, and the Issue driver applies the launch identity and run-id rules.
