## CL-D68 — The gate launch request and the designated-output read are packaged
**Clauses:** CL-D68-map, CL-D68-transport, CL-D68-record, CL-D68-tests

*Decision ID:* CL-D68
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#111` at its body, the design comment https://github.com/tetsuh/pi-tidd-agents/issues/111#issuecomment-5617260994, and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/111#issuecomment-5617536570
*Question:* Six exact-autofix runs on #113, #121, and #122 stopped before the writer on steps the parent assembled by hand although prose forbade each: a hand-edited or empty `outputSchema`; a parent-chosen `output:` file read instead of the runner's `structuredOutputPath` while a complete envelope sat at that path; the reviewed checkout's own helper executed as the checker; a cleanup with the removed workspace as its cwd; an invented operation name. Which of these documents should the package assemble, and under which class?
*Options and trade-offs:* Option A packages everything the issue names in one PR, including a process-spawning `validation_run`. Option B packages the read-only class first: `gate_result_read` reads the envelope from the runner's status record for a run id; `build_gate_launch` composes the launch request from the built expectation and the installed package's own payload blocks; `operator_capture` records the helper path and fails closed on a helper inside the target; `workspace_cleanup` and its builder refuse a cwd inside the workspace; an unknown operation names the nearest known ones. `validation_run` (#64 item 1) is deferred to its own decision. Option C packages `gate_result_read` alone, which removes the most frequent class and leaves the rest hand-assembled.
*Recommendation:* Option B.
*Owner choice:* Option B. This decision widens CL-D56's builder family by a read-only composer whose only I/O is two reads: the installed package's own authority files, host-trusted, and the supplied host-trusted expectation file it compares its input against: `build_gate_launch` emits the CL-D36 schema byte for byte (CL-D90 later moved the schema into the gate roles' agent definitions, so the request carries none, and CL-D91 moved the composed task into a payload file the request points to, the composer's one write until CL-D101 added the verification request beside it), copies the Every-gate, Sol-only, and owning-root role blocks verbatim with their digests recorded, carries the volatile envelope as data and the expectation file and packaged validator as two machine lines, and has no `output` field and no free-text envelope instruction. `gate_result_read` is the CL-D58 read path as an operation: the parent never chooses the path, and absent, empty, and unparsable output are distinct fail-closed codes naming the path. It widens CL-D44's declared field set by `build_gate_launch.expectation`, shape `data:build_gate_expectation`, pinned exactly like the five. This decision also raises the authority ceiling once more, from 140,000 to 150,000 bytes: the seven authority files measured 140,311 bytes with the two operations named in the invocation map and the transport section, 311 bytes over 140,000, and the headroom property is asserted at the raise (9,689 bytes), not against live growth.
*Rationale:* #83 → CL-D56 → CL-D61 established that a document the package composes cannot be composed wrong; the launch request and the read path were the two gate documents still outside that rule, and every lost run traces to one of them or to the checker running from the checkout it checks. Reading the package's own files is the one I/O a composer needs and the one that cannot vary with the target, which is why the widening is bounded to it.
*Validity and invalidation conditions:* Applies to the two operations, the helper-path record, the cleanup guard, and the CLI hint; the cleanup builder and the cleanup operation share one pure cwd predicate: the operation applies it to canonical filesystem identities and the builder to the request's strings, because filesystem identity is consumer-side state like every identity check. No workflow state, scheduling, child lifetime management, retry loop, or resume is added; CL-D36, CL-D39, CL-D51, and CL-D58 are unchanged, and `gate_result_read` changes where the parent reads from, not what counts as a verdict. PR #124 amended the read with one distinction: a step the runner still records as in progress is `run_in_progress`, neither a result nor a failure, because a workflow-layer completion notice fired at the launch of an asynchronous reviewer and the parent read and stopped a running child; the parent waits for the runner's own completion, and the read after it is the first read of a result, not a retry. A run the runner has already recorded as terminal is never `run_in_progress`, whatever its last step says, because nothing more will be written to it. A composer that writes, reaches the network or Git, or reads anything but those two classes — the installed package's authority files and the supplied expectation file — or a second source for the launch request, requires a new owner decision, as does any further ceiling raise.
