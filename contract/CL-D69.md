## CL-D69 — The evidence attestation carries no identity
**Clauses:** CL-D69-transport, CL-D69-payload, CL-D69-record, CL-D69-tests

*Decision ID:* CL-D69
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#111` at PR #123 head `dae7d09609469c5eed85db185b508accb5ff2b9a`, the options comment https://github.com/tetsuh/pi-tidd-agents/issues/111#issuecomment-5641950141, and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/111#issuecomment-5641956699
*Question:* Three review runs of PR #123 stopped at `evidence_records_invalid`: the convergence child validated its draft with the packaged validator (CL-D65) and then retyped the 64-character identities into the model-emitted `structured_output` tool, losing one character each time. Supplying the records inline as data did not remove the class, and the tool takes a value, never a file. Which shape should the child's `evidenceRead` attestation take?
*Options and trade-offs:* Option A: the child attests `source`, `kind`, and `readCompletely` only; the identity of each required entry lives in the parent's expectation, and the validator matches attestation entries to required entries by `source` and `kind`. Option B: the child writes its validated envelope to a file and `structured_output` carries a pointer the reader follows, an indirection in CL-D58's designated output with a stale-pointer surface of its own. Option C: no change; rerun until a run transcribes cleanly, roughly one success in three at 29 entries.
*Recommendation:* Option A.
*Owner choice:* Option A. The attestation record of both schema versions drops `identity`; a copied identity now fails schema validation because the record is closed. Assurance is unchanged: the child copied the identity from the task it was given, so the copy proved nothing the expectation did not, and the snapshot fingerprint binds the bytes the child read. The options comment cited CL-D47 as the rule pinning identities; it is the expectation built by `build_gate_expectation` (CL-D56, CL-D61) that pins them, and CL-D47 governs the fresh-finding namespace.
*Rationale:* The same shape as CL-D47: a hand-copied duplicate of a value the parent already holds can only ever be wrong, and every loss was a whole run that reflected nothing about the target. Omission, extra, duplicate, and incomplete attestations still fail closed, matched by `source` and `kind`.
*Validity and invalidation conditions:* Applies to `gate_result_validate`, the packaged schema, and the records `build_gate_launch` hands the child. It changes no round budget, grants no retry, and reduces no review duty. Reintroducing an identity in the attestation, or matching it by anything but `source` and `kind`, requires a new owner decision.
