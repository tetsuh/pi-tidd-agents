## CL-D88 — The workspace verification runs in the workspace the run created
**Clauses:** CL-D88-map, CL-D88-builder, CL-D88-record, CL-D88-tests

*Decision ID:* CL-D88
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#179` at its body and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/179#issuecomment-5795735529 (working session of 2026-09-23)
*Question:* Exact-autofix attempt 6 on PR #178 stopped BLOCKED in preflight: the parent composed the workspace verification with the operator checkout as `cwd`, and `workspace_verify` refused it with `identity_mismatch`. `build_workspace_verify` took `cwd` beside `created` and passed it through, although `created.path` already names the run-owned workspace. Where does the request's `cwd` come from?
*Options and trade-offs:* Option A derives `cwd` from `created.path` and refuses a `cwd` supplied beside it, so the parent has nothing to get wrong; it removes one declared input. Option B keeps `cwd` as an input and refuses it unless it equals `created.path`, which moves the refusal from the guard to the builder but still asks the parent for the path. Option C restates the rule in the map and leaves the builder, which is safe because the guard fails closed, and spends a whole run each time.
*Recommendation:* Option A.
*Owner choice:* Option A (https://github.com/tetsuh/pi-tidd-agents/issues/179#issuecomment-5795735529). `build_workspace_verify` takes `created` and, optionally, `transition`; the request runs in `created.path`. A `cwd` beside `created` is refused as an input even when it agrees, because the builder has one source for that fact; a workspace path that is empty, not absolute, or carries a NUL byte or a lone surrogate is refused at build time. The same derivation serves a linked workspace and a retained clone, since `workspace_verify` verifies either. It is the sixth request of its class packaged this way, after CL-D56, CL-D68, CL-D73, CL-D81, and CL-D84, and takes the shape of CL-D82's gate-launch `cwd` and CL-D84's cleanup.
*Rationale:* The guard was right and the run still ended in preflight, because the only thing between a correct rule and a lost run was the parent typing a path the package already held. Every earlier member of this class ended with the document removed rather than the rule restated.
*Validity and invalidation conditions:* Applies to `build_workspace_verify` and the requests it composes. `workspace_verify` itself, its identity checks, and its transition rules are unchanged, and a caller that composes the `workspace_verify` request directly still supplies its own `cwd` and is still checked by the guard. Taking a `cwd` from anything but `created.path`, or accepting one beside it, requires a new owner decision.
