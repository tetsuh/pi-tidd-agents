## CL-D91 — The gate launch carries a pointer to a verified payload file
**Clauses:** CL-D91-payload, CL-D91-verify, CL-D91-record, CL-D91-tests

*Decision ID:* CL-D91
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#188` at its body and the owner choices https://github.com/tetsuh/pi-tidd-agents/issues/188#issuecomment-5851025142 and https://github.com/tetsuh/pi-tidd-agents/issues/188#issuecomment-5851068857 (working session of 2026-09-27)
*Question:* Exact-autofix attempt 3 on PR #183 stopped with `gate_launch_input_mismatch` before any verdict. The packaged launch carried a 14,283-character task; the parent's subagent call carried 9,968 characters, first differing at character 4,872 inside the envelope's base64 diff. After CL-D90 took the schema out of the parent's hands, the task was the last large document it transcribed. How does the task reach the child without the parent transcribing it?
*Options and trade-offs:* Option A writes the complete task to a run-owned payload file and makes the request's task a pointer the child verifies by digest; the parent transcribes a few hundred characters, and a corrupted pointer or file fails closed in the child. Option B moves only the bulk (the diff, the expectation, the evidence records) to files and keeps the invariant blocks inline, which shrinks the transcription to about 4–5 KB without removing it.
*Recommendation:* Option A.
*Owner choice:* Option A (https://github.com/tetsuh/pi-tidd-agents/issues/188#issuecomment-5851025142). `build_gate_launch` composes the task exactly as before and writes it to `gate-payload-<gate>-<invocation>-<digest prefix>.md` beside the expectation file, mode 0600, never overwriting: an identical file is reused and a different one is refused (`payload_exists_different`). The expectation path must be absolute and outside every Git work tree (`payload_location_invalid`), so neither the operator checkout nor the workspace gains a file. The expectation path must be absolute in both modes and the payload location is judged where it resolves, inside the temporary directory. The request's `task` is the pointer: the exact command that runs `gate_payload_verify`, carrying the payload path and its SHA-256 exactly once each, the instruction to end without any structured output when it fails (so a corrupted pointer or file is a zero-output transport failure, not a malformed result), and otherwise to read the file the verifier's result names (`path`, resolved) completely and follow it verbatim, so no unauthenticated copy of the path exists for the child to follow; a planted link or other entry at the payload name is refused; the result also returns `payloadPath` and `payloadSha256`. `gate_payload_verify` takes `path` and `sha256` and refuses an unreadable file (`payload_unreadable`) or a different digest (`payload_digest_mismatch`). The packaged-helper alarm resets from 290,000 to 300,000 bytes (https://github.com/tetsuh/pi-tidd-agents/issues/188#issuecomment-5851068857): the payload file and its verification put the helpers at 292,160 bytes, and the payload code lives in its own `payload.js` under the unchanged per-file alarm.
*Rationale:* Transcription fails in proportion to what is transcribed. Every earlier member of this class ended with the composed document leaving the parent's hands, and the pointer is what remains when the document itself cannot: short enough to copy, and checked by a digest the parent never computes.
*Validity and invalidation conditions:* Applies to `build_gate_launch`'s request and result, the payload file, and `gate_payload_verify`. The composed task, its invariant blocks, the expectation file, the result read, and every gate's authority are unchanged. Putting the payload back inline, writing it inside a Git work tree or over another file, or letting a gate proceed on an unverified payload requires a new owner decision. CL-D101 later took the path and the digest out of the pointer: the launch names a verification request the builder wrote, and the child runs it.
