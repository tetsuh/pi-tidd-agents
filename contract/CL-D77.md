## CL-D77 — Every exact-autofix run ends with the owner publication artifacts
**Clauses:** CL-D77-addendum, CL-D77-record, CL-D77-publisher, CL-D77-readme, CL-D77-cl-d33-note

*Decision ID:* CL-D77
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#141` at its body and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/141#issuecomment-5736638735 (working session of 2026-09-19)
*Question:* A review-only run ends by drafting `review-comment.md` and `publish-review.sh` (CL-D33); the owner publishes by running the script. The exact-autofix addendum asked only for a proposed summary draft to be reported. The two autofix runs of PR #139 reached a terminal outcome, one of them `MERGE_READY`, and wrote no artifact, so the owner had nothing to run and a watcher waiting on the artifact waited until it was stopped by hand. What does an exact-autofix run leave behind?
*Options and trade-offs:* Option A drafts the CL-D33 artifacts at every terminal outcome, as review-only does, so every run ends with something the owner can publish and the same signal a watcher already reads. Option B drafts them on `MERGE_READY` only, which leaves a stopped run with no artifact and no signal. Option C records their absence as the contract, which removes the surprise and nothing else.
*Recommendation:* Option A.
*Owner choice:* Option A (https://github.com/tetsuh/pi-tidd-agents/issues/141#issuecomment-5736638735), narrowed after the pre-push adversarial review (https://github.com/tetsuh/pi-tidd-agents/issues/141#issuecomment-5738167081). Every terminal outcome still ends with the summary draft; when the repository, the pull request, and the public head are resolved and unambiguous, that draft is the two CL-D33 artifacts, drafted from the packaged template exactly as review-only drafts them, bound to the current verified public head and saying whether the gates reviewed it. When any of the three is unresolved, as after a preflight stop, an unknown push outcome, an interrupt, or a foreign target, nothing is drafted and the report states `not_drafted(<reason>)`. The parent reports the paths, the digest, the repository, pull request, and head, and the command, and never executes it; the owner executing the generated script remains the one owner-approved comment action the addendum already describes. So that the script's guards cover the binding the addendum states, the template now also refuses a draft pull request, and binds the base OID and the head repository and branch at its first identity read and requires them unchanged at the read immediately before POST. This changes the CL-D33 template for review-only artifacts too, which fail closed the same way. A pull request whose head repository no longer exists, as after a fork is deleted, can then no longer be published by the generated script in either mode; that is the same fail-closed binding, stated so it is not mistaken for a defect. That binding brackets the script's own run, from its first identity read to the read before POST; it does not compare those values with the ones the review saw, which the artifacts do not carry. Duplicate detection keys on the exact generated summary, through the marker's digest of its visible bytes, not on the head alone: two artifacts drafted for one head with different bodies can both be published, and a per-head guard would need a new owner decision. The head the artifacts are bound to, the reviewed head in review-only, is checked through the script's own metadata as before, and carrying the reviewed base or head branch too would need a new owner decision.
*Rationale:* The addendum already required a summary draft and already placed posting outside autofix as a one-shot owner action; CL-D33's artifacts are that action's packaged form, reviewed once and used by every review-only run. Drafting them costs the run no authority, and leaving a stopped run without them is what made the PR #139 outcomes recoverable only from the session's screen.
*Validity and invalidation conditions:* Applies to the exact-autofix terminal report. The autofix grant does not widen: `aggregate summary posting` stays outside it, the run never executes the script, and CL-D33's template gains only the identity checks above. The mode-dispatch invariant is unchanged too: the addendum names the packaged template it copies, not the review-only reference. This widens the scope of CL-D33, which applied only to review-only, to the exact-autofix terminal report: the drafting is granted here, and CL-D33 still grants autofix no action. Issue #148 joined the identity fields with the unit separator instead of a tab, so an empty field keeps its place rather than shifting the next value into it, and gave the base OID, head repository, and head branch each its own refusal (owner deferral, https://github.com/tetsuh/pi-tidd-agents/pull/146#issuecomment-5741293834). Issue #149 then bound the identity tuple with that same separator, required the base OID, head repository, and head branch to be strings, the draft state to be a boolean, and the pull-request number to be a number, and required the record to carry exactly the nine fields the filter emits. Valid publication behaviour is unchanged by both; what is newly refused is malformed or ambiguous identity evidence, each case of which reached POST before the correction (owner choice DEC-PR149-IDENTITY-HARDENING-SCOPE, https://github.com/tetsuh/pi-tidd-agents/pull/149#issuecomment-5770898809). Letting a run execute the script, dropping the artifacts from a terminal outcome whose target is resolved, or loosening the template's identity checks, requires a new owner decision.
