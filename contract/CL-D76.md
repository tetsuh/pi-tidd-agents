## CL-D76 — The cleanup builder takes its cwd from the receipt
**Clauses:** CL-D76-record, CL-D76-tests

*Decision ID:* CL-D76
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#142` at its body and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/142#issuecomment-5733269978 (working session of 2026-09-19)
*Question:* An exact-autofix run on PR #139 built its terminal cleanup with `build_workspace_cleanup` and gave it the workspace being removed as the `cwd`. The builder refused with `cleanup_cwd_inside_workspace`, as CL-D68 requires, and the run ended `BLOCKED` with the workspace retained, after its corrections had been published. The receipt the builder is given already states the repository the workspace was created from. Who chooses the cleanup `cwd`?
*Options and trade-offs:* Option A removes `cwd` from the builder's inputs and takes it from the receipt, so no caller can state a wrong one; the input freeze CL-D56 set changes, which is why this is a decision. Option B keeps `cwd` as an optional input defaulting to the receipt's repository, which keeps every existing caller working and leaves the PR #139 request as refusable as before. Option C states in the invocation map which `cwd` a cleanup uses and changes no code, which recurs whenever a run misses the sentence.
*Recommendation:* Option A.
*Owner choice:* Option A (https://github.com/tetsuh/pi-tidd-agents/issues/142#issuecomment-5733269978). `build_workspace_cleanup` takes `created` alone; the packaged CLI and the builder itself both refuse a `cwd` as an unknown request field. The receipt states the repository twice, equal at creation; the builder reads the copy inside the stored creation identity, which is the one `workspace_cleanup` holds against the stored receipt, rather than the unchecked one beside it. That choice between the two copies is this record's reading of the owner's decision, not a further owner choice. After three review rounds each found one more receipt shape the builder certified and the operation then refused, the owner fixed where the builder's refusals end (https://github.com/tetsuh/pi-tidd-agents/issues/142#issuecomment-5739376128): the builder refuses a receipt no genuine `workspace_create` output can be, meaning a string or key carrying a NUL byte or a lone surrogate, nesting beyond any genuine receipt, and a creation identity whose keys, key order, field types, or constants differ from what `workspace_create` writes, key order included because the operation compares the stored identity as JSON. Agreement of values with the stored file, and where the run root sits relative to the stored receipt and the workspace path, stay with `workspace_cleanup`, which refuses them before removing anything; they are known residuals of this record, not defects of the builder. The CL-D68 predicate still runs on that derived cwd, so a receipt stating a path at or inside the workspace, or a relative one, is refused before any request exists.
*Rationale:* The builder exists so the parent does not transcribe what a producing result already states (CL-D56); the cwd was the one field of this request it still transcribed, and the only one the run got wrong. A value the receipt states cannot be misstated by the caller, and the operation compares it with the stored file anyway.
*Validity and invalidation conditions:* Applies to `build_workspace_cleanup`. `workspace_cleanup` keeps its inputs and its CL-D68 guard unchanged, so a request assembled by hand still states its own `cwd` and is still refused when that cwd is inside the workspace. CL-D49 and CL-D75 are unchanged. Accepting a caller-stated cwd in the builder again, or deriving it from anything but the stored creation identity, requires a new owner decision.
