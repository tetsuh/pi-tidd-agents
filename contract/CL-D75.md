## CL-D75 — A cleanup that cannot remove the root it emptied names it and still succeeds
**Clauses:** CL-D75-record, CL-D75-tests

*Decision ID:* CL-D75
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#132` at its body and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/132#issuecomment-5712780270 (working session of 2026-09-17)
*Question:* `workspace_cleanup` now removes the run root it emptied. When the worktree and the receipt are gone but that root cannot be removed, what does the operation return? Reporting `removed: true` asserts an outcome that did not happen, which the Sol gate raised as `ADV-134-SILENT-RMDIR-FAILURE`; reporting a failure makes a cleanup whose work is complete `BLOCKED`, and because the receipt is unlinked first, nothing can re-authorize a retry.
*Options and trade-offs:* Option A returns success and names the leftover in the result, at the cost of one new field on a result `test/issue-80-cleanup-terminal.test.js` pins verbatim, so the shape cannot change without a reviewed decision; CL-D44 freezes cross-operation request fields and does not reach an output, so it is that pin, not that freeze, which makes this a decision. Option B returns a failure, which satisfies the issue's first acceptance criterion literally but rebuilds the class CL-D49 exists to remove, approached from the other side, and drops the terminal evidence unless it is carried in the error details. Option C keeps the silent success and records the limit in prose, answering a Major by interpretation rather than by measurement.
*Recommendation:* Option A.
*Owner choice:* Option A (https://github.com/tetsuh/pi-tidd-agents/issues/132#issuecomment-5712780270). A successful `workspace_cleanup` result carries `retainedRoot`: the run root when it is still standing, and `null` when it is observed gone: a parent that denies even a lookup hides a root that is still standing, and reading it any more forcefully would reintroduce the failure this decision removes. Whether it went is observed rather than inferred from the refusal, because the same leftover answers `ENOTEMPTY` when the directory is not empty and `EACCES` when its parent will not allow the removal, so an errno test makes one identical filesystem state succeed and the other fail on a permission bit the operation was never asked about.
*Rationale:* The leftover is a fact about the run root, not about the work: the worktree is gone and the receipt is unlinked before the removal is attempted, so a failure there ends a run that had finished, and the receipt it would need to re-authorize a retry no longer exists. CL-D49 recorded roughly ninety such runs, and a failure here would be the same shape reached from the other direction. Naming the leftover costs one field and removes the class: the result stops claiming what did not happen, and a caller that cares can read it. The measurement that opened Issue #132 is unchanged by this: one `npm test` left twelve run roots before the removal and five after, and every root a cleanup emptied is gone.
*Validity and invalidation conditions:* Applies to the `workspace_cleanup` success result. CL-D49 is unchanged and uninvalidated: its invalidation clause names the removed path and the terminal head and tree ceasing to be returned, and all three are still returned beside the new field; a cleanup that fails remains `BLOCKED` exactly as CL-D49 states, because this decision adds no failure. `retainedRoot` is the one field this decision grants; another, or any use of it to sweep, expire, or report roots left by runs that never called cleanup, requires a new owner decision, which Issue #132 already reserves for that accumulation.
