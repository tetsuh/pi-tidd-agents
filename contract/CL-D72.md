## CL-D72 — The focused validation is packaged and the alarm is reset for it
**Clauses:** CL-D72-map, CL-D72-map-moved, CL-D72-route-review-only, CL-D72-route-shared, CL-D72-route-autofix, CL-D72-record, CL-D72-tests

*Decision ID:* CL-D72
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#64` item 1, deferred from CL-D68, at the design comment https://github.com/tetsuh/pi-tidd-agents/issues/64#issuecomment-5654184082 and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/64#issuecomment-5654208805 (`A A A`)
*Question:* The CL-D39 recovery table names "validation harness could not run" as a terminal class, but nothing produced the distinction: the parent ran the toolchain through its own shell and read the output itself. Should the package spawn and classify the focused validation, what does that do to the helper boundary and its alarm, and should the required-evidence set be derived by the package as well?
*Options and trade-offs:* Three questions, each with its options in the design comment. For the operation, Option A packages `validation_run`, an argv spawn that classifies its own outcome; Option B packages only a pure classifier of a spawn the parent still performs; Option C leaves item 1 to prose. For the alarm, Option A resets it to 240,000; Option B to 260,000; Option C keeps 220,000 and trims, the recorded anti-pattern. For the evidence set, Option A derives it in the package; Option B does not.
*Recommendation:* Option A on all three.
*Owner choice:* Option A on all three. `validation_run` takes `cwd`, an argv `command`, and an optional `timeoutMs`, never a shell string; the cwd must be the toplevel of a Git checkout, verified through the allowed `rev-parse`; the child runs under an explicit environment allowlist rather than the inherited environment: `PATH` and `HOME`, so an argv program and its toolchain resolve, the temporary-directory and user-name variables, and the Windows system variables a process there needs, each matched by its exact name (without case on Windows), with `LC_ALL` and `LANG` fixed to `C` and `GIT_TERMINAL_PROMPT` to `0`; every other inherited variable, whether an interpreter or loader hook, a credential, an agent socket, or a command-resolution control, is dropped, while `git` and `gh` keep the package's sanitized environment and its Git isolation. Node propagates `NODE_V8_COVERAGE` from its own environment unless the child's carries the name, so the validation environment carries the name itself and undefined; and on Windows `PATHEXT` and `ComSpec`, which decide how a command shell and npm resolve a bare name, are pinned to the system defaults rather than inherited, while the process spawner forwards a few Windows system variables of its own that no allowlist can withhold. Each of the request's own fields is read once and the command runs as that copy, so an inherited field is not the request's, an own field left undefined is absent, and a request that throws while it is read is refused at the request: the program is a non-empty string, every later argument is any string, the empty string included, the argv holds at most 65,536 elements, and the child receives each argument exactly as the evidence names it, so a program, an argument, or a cwd that holds a NUL or is not well-formed Unicode, which could not reach the child as written, is refused at the request. Both toplevel checks, here and in `required_evidence_set`, take Git's whole answer, so a subdirectory whose name begins with a newline is not mistaken for the toplevel, and a spawn error Node throws at once still carries the system's own code as its reason. It returns `passed` when the command exits 0, and fails closed as `validation_failed` at phase `validation` when the command ran and exited nonzero by itself, or as `harness_failed` at phase `spawn` when it could not run or did not finish — a spawn error, a signal, or the timeout — each carrying the bytes, the SHA-256, and a bounded tail of both streams. The timeout is enforced by SIGKILL and decides the outcome, whatever exit a killed command then reports, and a stream beyond 16 MiB is `harness_failed` with reason `output_limit`, reporting the bytes captured within that bound. It interprets nothing about the output, and each outcome stays terminal under CL-D39. The recovery row's key becomes `validation_run@focused_validation`, naming the packaged operation as every other row does. The design comment had written `validation_run@spawn`; the owner chose the step name (https://github.com/tetsuh/pi-tidd-agents/issues/64#issuecomment-5662628859, option A on the options at https://github.com/tetsuh/pi-tidd-agents/issues/64#issuecomment-5656713435) because the table's own rule makes a key's phase part the workflow step, while `spawn` stays the phase field of the operation's own error envelope, while the row's Failure cell names its code, `harness_failed`. This is the package's one spawn of anything but `git` and `gh`: the issue-59 model recognizes exactly one spawn site whose program is neither `git` nor the gh transports' literal `'gh'`, in `validation.js`. That guard is a structural check of reviewed source bounded to direct references, not a JavaScript evaluator (owner option A, https://github.com/tetsuh/pi-tidd-agents/issues/64#issuecomment-5670651510, on the options at https://github.com/tetsuh/pi-tidd-agents/issues/64#issuecomment-5670561710): read from the syntax tree that Node's own bundled parser builds, so that strings, templates, regular expressions, comments, and division are told apart by the grammar rather than guessed, a spawn primitive may appear only as a direct call, as its definition or export in `process.js`, or in a destructured import that does not rename it, and a literal name counts as a reference wherever it is written, so a computed member such as `module.exports['run']`, a computed key, a string argument such as `Reflect.get(module.exports, 'run')`, or a rest element gathering an import is refused, and `require` appears only as a direct call; the text `child_process`, and any string literal whose value names it, appears only in `process.js`'s one import, for `execFile` and `execFileSync`; every call of `transport` or `defaultTransport` passes the literal `'gh'`, and each gh transport spawns only the literal `'gh'`; a module loader other than `require`, `getBuiltinModule` or `mainModule`, appears nowhere; a literal Git argument list carries no `-c` configuration pair of its own; `eval`, the `Function` constructor, and process bindings are refused as references of any form — `eval`, `Function`, `constructor`, `global`, `globalThis`, and a dynamic `import()` appear nowhere in code, and `process` appears only as a member access other than `binding`, `_linkedBinding`, `dlopen`, and `execve`, or as `bind(process)`, and no member named `binding`, `_linkedBinding`, `dlopen`, or `execve` is called; and a form outside this bound is not a finding against the guard. The aggregate smoke alarm resets from 220,000 to 240,000 bytes on the CL-D37 review recorded in the design comment — the 16,000 bytes since CL-D71 were PR #123's reproduced and recorded corrections, the per-file alarm and every structural assertion held, and `launch.js` is split into `envelope.js` so the per-file alarm is not raised. `required_evidence_set` derives a gate's required-evidence set as a read-only observation: the paths the change touches that exist at the head, plus `CONTRACT.md` and `README.md`, each identified by the SHA-256 of its blob at the head through the allowed `diff`, `ls-tree`, and `cat-file`, plus the identity records the parent supplies unchanged; it is an observation rather than a builder because it reads Git, which the builders paragraph forbids to every builder, whose only I/O is `build_gate_launch`'s two file reads. The derived set carries only what `required_evidence_check` can verify, a regular blob (`100644` or `100755`) at the head; a changed symlink or submodule pointer is excluded and named with its mode in the result, and the gates still receive that change through the diff the envelope carries (owner option A, https://github.com/tetsuh/pi-tidd-agents/issues/64#issuecomment-5663434628, on the options at https://github.com/tetsuh/pi-tidd-agents/issues/64#issuecomment-5663359233). A changed path whose bytes are not valid UTF-8 fails closed as `path_encoding`, because evidence names a path as text, and both Git listings are matched by their bytes so that two names that decode alike never stand in for each other. Each Git read carries its own bound rather than the process default — a listing up to 256 MiB, a blob up to 256 MiB measured before it is read, every other read up to 64 KiB — and because one buffer covers both streams of a synchronous spawn, the child's error stream goes to a file of its own in the package's isolation root, measured after the read and refused beyond 64 KiB, a threshold on what a read may carry rather than a cap on what Git may write, so a read beyond its bound fails closed as `output_limit` naming it, and a read whose warnings pass that bound fails closed naming the error stream and the bytes Git wrote. A present authority file that is not a regular file is excluded with its mode, and `absent` names only a file the head does not carry.
*Rationale:* The same class CL-D68 packaged: a document the parent assembled by hand at a boundary where a defect is terminal. A harness fault read by eye ended runs after a correct correction, and every review of PR #123 needed an operator note to keep the required-evidence set to what the gates review. Packaging the spawn puts the classification where the evidence is, and deriving the set makes it deterministic and reviewable.
*Validity and invalidation conditions:* Applies to `validation_run`, `required_evidence_set`, the recovery row key, the alarm value, and the spawn-site rule. CL-D103 later made `CONTRACT.md` the preamble and the record index, each record its own file, so a change to one record carries that record's file and no other. It adds no recovery, retry, or relaxation of CL-D39 and no mutation, publication, or writer authority; the operation runs what the parent names and decides nothing about what a failure means. A second non-git spawn site, a shell string, a cwd below a toplevel, a program allowlist, or a further alarm raise requires a new owner decision.
