## CL-D52 — The stability digest ignores foreign-branch configuration
**Clauses:** CL-D52-tests

*Decision ID:* CL-D52
*Kind:* fail-closed operator-stability boundary
*Target and revision:* `tetsuh/pi-tidd-agents#91` at its initial body and the owner's live instruction that linked worktrees are the intended development model and separate clones are a real cost
*Question:* Should the operator config-stability digest keep covering branch-scoped configuration for branches other than the checked-out one, when writing exactly such entries is what ordinary linked-worktree development does?
*Options and trade-offs:* Keeping the all-bytes digest keeps killing live reviews for configuration the run never reads — two BLOCKED runs demonstrated it, PR #77 via `push -u` and PR #90 via `checkout -b` auto-tracking, both with clean checkouts, unchanged HEAD, and zero workflow mutations. Forbidding parallel work in worktrees pushes the cost onto the operator permanently. Normalizing the digest to ignore foreign-branch sections tolerates the observed churn while leaving every behavior-relevant byte pinned.
*Recommendation:* Normalize the stability digest only; change nothing else.
*Owner choice:* As recommended. `branch.<name>.*` entries are invisible to the stability digest for every `<name>` other than the operator's currently checked-out branch, and for all names when HEAD is detached; branch names may contain dots and the subsection is parsed as everything between `branch.` and the final component. The checked-out branch's own entries stay pinned, every non-branch key stays pinned, the unsafe-key scan keeps covering the full configuration including foreign branch sections, and the mid-preflight double-read keeps comparing raw bytes so an in-flight write still stops the run.
*Rationale:* The digest exists to prove the operator baseline did not move in ways that could change what the run does or publishes. A foreign branch's tracking configuration cannot: the reviewed run never reads a foreign branch's configuration — publication is an explicit-refspec push from the isolated workspace under sanitized environment and config isolation, remote URLs are bound separately in the identity baseline, and the checked-out branch's tracking is both digested and independently captured as `trackingRef`. What the two incidents wrote is therefore churn with no reader inside the run, and treating it as movement converted normal development into whole-run losses after validation had already passed. The boundary is drawn at the narrowest line the evidence supports: sections other than `branch.*` are never ignored, and even a `branch.*` key is refused by the unsafe-key scan if it ever matches an unsafe pattern.
*Validity and invalidation conditions:* Applies to the stability digest computed by `assertSafeRepositoryConfig`. It weakens no unsafe-key rejection, no raw-byte instability check, no identity binding, and no cleanliness rule. If the workflow ever reads a foreign branch's configuration — a multi-branch operation, a tracking-derived default anywhere outside the checked-out branch — the invisibility recorded here is invalidated for exactly those keys. Widening the ignored set beyond foreign `branch.*` sections requires a new owner decision.
