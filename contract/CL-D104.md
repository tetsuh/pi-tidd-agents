## CL-D104 — /tidd-pr runs through the packaged driver
**Clauses:** CL-D104-record, CL-D104-skill, CL-D104-readme, CL-D104-tests

*Decision ID:* CL-D104
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#224` at its body, and #196 owner decisions D2 and D4 (https://github.com/tetsuh/pi-tidd-agents/issues/196#issuecomment-5870929892)
*Question:* The packaged drivers (CL-D93, CL-D96) were reached only through an operator-side launcher outside the package. `/tidd-pr` loaded the Skill, and the parent followed its prose step by step, hand-composing the helper requests the drivers already build; #194 records consumer runs lost to that composition after the review-only driver had merged. How does `/tidd-pr` reach the driver?
*Options and trade-offs:* Option 1 keeps the prose path and the launcher; each hand-composed request remains a way to lose a run. Option 2 gives the Skill a dispatch section that the parent reaches after the precondition guard, mode parsing, preflight and the target-kind boundary: the parent runs the packaged driver, makes exactly the `subagent` call it prints, and runs the command it names next, until a terminal outcome. The prompt stays a thin dispatcher (DEC-I22-PROMPT-AUTHORITY-001).
*Recommendation:* Option 2.
*Owner choice:* Option 2, as #196 decided (D2: the parent only makes printed `subagent` calls; D4: the prompt and Skill switch is the third pull request). The section passes the target's repository to the driver, so a pull request number is never read against the checkout's repository by default. The parent judges an outcome by what the driver prints, never by its exit status: `FINISHED` ends the round with the two drafted publication artifacts, which the parent never runs; any other end is reported and stops, with no retry; and only a driver that says the pull request stays on the prose path (a head in another repository, or a head or base that is not local) sends the parent on to Mode dispatch. The parent never interrupts, pauses, steers or cancels a running gate or writer. The Skill's other sections and the mode references stay as they are, as the specification the driver and the gates implement (D2), and they still govern the prose path. The authority files grow by the section alone and stay under the 156,000-byte ceiling of CL-D85, so no guard is raised. `README.md` names the one way to run a round and where the validation commands come from (CL-D97).
*Rationale:* Each prose-level fix of hand composition (CL-D56 through CL-D91) removed one composed document from the parent; the driver removes the rest at once, and a parent that only relays the printed call has nothing left to compose. Judging by printed tokens follows the driver's own report: a terminal outcome other than `MERGE_READY` still drafts the publication artifacts and exits nonzero.
*Validity and invalidation conditions:* Applies to `/tidd-pr` and `/skill:closed-loop-pr` for a pull request the driver accepts. Letting the parent compose a request the driver builds, judge an outcome by exit status, or interrupt a running gate, or removing the dispatch section, requires a new owner decision.
