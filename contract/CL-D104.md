## CL-D104 — /tidd-pr runs through the packaged driver
**Clauses:** CL-D104-record, CL-D104-skill, CL-D104-readme, CL-D104-forward-d19, CL-D104-forward-ceiling, CL-D104-tests

*Decision ID:* CL-D104
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#224` at its body, and #196 owner decisions D2 and D4 (https://github.com/tetsuh/pi-tidd-agents/issues/196#issuecomment-5870929892)
*Question:* The packaged drivers (CL-D93, CL-D96) were reached only through an operator-side launcher outside the package. `/tidd-pr` loaded the Skill, and the parent followed its prose step by step, hand-composing the helper requests the drivers already build; #194 records consumer runs lost to that composition after the review-only driver had merged. How does `/tidd-pr` reach the driver?
*Options and trade-offs:* Option 1 keeps the prose path and the launcher; each hand-composed request remains a way to lose a run. Option 2 gives the Skill a dispatch section that the parent reaches after the precondition guard, mode parsing, preflight and the target-kind boundary: the parent runs the packaged driver, makes exactly the `subagent` call it prints, and runs the command it names next, until a terminal outcome. The prompt stays a thin dispatcher (DEC-I22-PROMPT-AUTHORITY-001).
*Recommendation:* Option 2.
*Owner choice:* Option 2, as #196 decided (D2: the parent only makes printed `subagent` calls; D4: the prompt and Skill switch is the third pull request). The section applies to a pull request of the repository of the current checkout and passes that repository to the driver, run from the checkout's top-level directory, so a pull request number is never read against another repository. The parent relays the call on each `NEXT:` line unchanged, waits for the runner's own completion of that run, and runs the command on the `NEXT:` line itself; commands inside the call are the subagent's. A `WAIT:` line means the run has not completed, and running its command again after completion is not a retry. A refused call, a call that returns no run id, and a command killed by a timeout are reported and stop the run. The parent judges an outcome by the lines the driver prints, never by its exit status: a driver that says to review the pull request on the prose path (a head in another repository, commits that are not local, or a diff that is not UTF-8) sends the parent on to Mode dispatch in the parsed mode, whatever reference the message names; otherwise a line beginning `FINISHED comment=` ends the round, and the parent reports from that line to the end verbatim and never runs the publication script; any other end is reported and stops, with no retry. The parent never interrupts, pauses, steers or cancels a running gate or writer. This narrows CL-D19 and Mode dispatch, which read exactly one mode reference after mode parsing, to the prose path. The Skill's other sections, the shared references and the mode references stay as they are, as the specification the driver and the gates implement (D2), and they still govern the prose path. The driver reads the Issue a pull request serves from a `Closes #N`, `Fixes #N` or `Resolves #N` reference in its body; `/tidd-pr` passes no `--issue`, so a pull request without one stops `BLOCKED` naming the gap, and the operator adds it or runs the driver directly. The section takes the authority files past the 156,000-byte ceiling of CL-D85: they measured 156,176 bytes on this change, so the ceiling rises to 162,000 bytes on the CL-D43 terms, with the headroom asserted at the raise. `README.md` names the one way to run a round and where the validation commands come from (CL-D97).
*Rationale:* Each prose-level fix of hand composition (CL-D56 through CL-D91) removed one composed document from the parent; the driver removes the rest at once, and a parent that only relays the printed call has nothing left to compose. Judging by printed tokens follows the driver's own report: a terminal outcome other than `MERGE_READY` still drafts the publication artifacts and exits nonzero.
*Validity and invalidation conditions:* Applies to `/tidd-pr` and `/skill:closed-loop-pr` for a pull request the driver accepts. Letting the parent compose or change a request the driver builds, judge an outcome by exit status, or interrupt a running gate, or removing the dispatch section, requires a new owner decision.
