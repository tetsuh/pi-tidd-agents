## CL-D74 — The post-commit message check is packaged
**Clauses:** CL-D74-operation, CL-D74-addendum, CL-D74-record, CL-D74-tests

*Decision ID:* CL-D74
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#114` at its body and the owner choice https://github.com/tetsuh/pi-tidd-agents/issues/114#issuecomment-5699413308 (working session of 2026-09-16)
*Question:* An exact-autofix run created a correct commit and then stopped as `BLOCKED(reason=local_commit_unpushed)`. The contract told it to run `git log -1` with the format that shows a message and compare the stored bytes exactly, but not how to capture that output. The format appends one LF to the stored body and a shell capturing it strips every trailing LF, so the exact comparison the contract requires could not be made by the means the contract named.
*Options and trade-offs:* Option A packages the check as an operation that reads the commit object and compares bytes, the shape CL-D68 and CL-D73 used for steps a run was getting wrong by hand. Option B corrects the prose alone, stating that the format appends one LF and exactly one must be stripped, or that both sides are written to files and compared; the instruction stays something each run performs by hand. Option C does both.
*Recommendation:* Option A.
*Owner choice:* Option A (https://github.com/tetsuh/pi-tidd-agents/issues/114#issuecomment-5699413308). Packaged `message_verify` takes the workspace and the approved message, reads the commit object through the already-reviewed `cat-file` command, and compares the stored bytes with the approved message put through the cleanup Git itself applies to a `-F` message: trailing whitespace off every line, leading and trailing blank lines dropped, and runs of blank lines collapsed to one. Reading the commit object needs no byte added and none removed, so nothing has to be stripped and no shell is involved; `git log` stays outside the reviewed Git-command allowlist. The addendum now names the operation where it named the format, and pins the mode it verifies against: `git commit -F --cleanup=whitespace` in both the bounded batch and the CL-D25 commit rule, so creation and verification share one explicit cleanup contract and repository configuration cannot set them apart (CONV-129-CLEANUP-CONFIG-001). The addendum's recorded guard resets from 28,000 to 29,000 bytes for that pin on the CL-D37 review recorded here (owner choice, https://github.com/tetsuh/pi-tidd-agents/issues/114#issuecomment-5700780731): no prose was trimmed to make room, which is the route CL-D57 reserves this reset for, and both helper alarms are untouched.
*Rationale:* The contract already knew what Git stores and what the format adds; `test/issue-35-failure-injection.test.js` pins both. What failed was that the comparison was left to each run to compose, and one composition that follows the words exactly cannot succeed. A run that cannot perform the check the contract requires stops with a correct commit unpushed, which costs the whole batch.
*Validity and invalidation conditions:* Applies to the post-commit message check of the exact-autofix bounded batch. It adds one CLI operation, which is the CL-D37 boundary this decision reviews: the packaged helpers stay inside both smoke alarms and the operation spawns only the literal `git` with an allowlisted command. It grants no new authority: the operation reads, never writes, and the `AFTER_COMMIT` and `BEFORE_PUSH` guards are unchanged. What the pin does not reach is Git's own re-encoding: a message carrying a Unicode noncharacter is stored re-encoded and no longer equals the approved bytes, while ordinary text beyond the BMP round-trips exactly. Reading the message by any other means, or widening the Git-command allowlist for it, requires a new owner decision.
