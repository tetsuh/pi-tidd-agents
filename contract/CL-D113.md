## CL-D113 — The clause pins of the review-only reference move to the code and the records
**Clauses:** CL-D113-record, CL-D113-forward, CL-D113-forward-d54, CL-D113-gaps, CL-D113-resume, CL-D113-tests

*Decision ID:* CL-D113
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#272`, pull request B2 of #249, under the owner's option (a) (https://github.com/tetsuh/pi-tidd-agents/issues/249#issuecomment-6105220135) and the corrected order (https://github.com/tetsuh/pi-tidd-agents/issues/249#issuecomment-6105250786), after B1 (CL-D112)
*Question:* Since CL-D111 no run reads `references/review-only.md` as guidance; `driver/review.js` still hashes it into `contractInput` until the last pull request of #249 deletes it. Twenty-five clause pins across twenty-two records name the file, and sixteen test files read it, eleven of them as the statement of a rule. Where do those pins go, so that the deletion changes no pin, when the driver files have under six hundred bytes of aggregate headroom and `driver/run.js` about a hundred under its own alarm?
*Options and trade-offs:* Option A repoints each pin as CL-D112 did: a rule the packaged review-only driver implements goes to the driver or helper code where that file carries the record's marker, a marker added in a driver comment, new or existing, where a few bytes buy a code pin; every other rule goes to the record's own sentence, added where the record lacked one. Option B pins every implemented rule to the code and raises both driver alarms on CL-D43's terms for the marker comments, a contract change inside a behaviour-neutral pull request. Option C moves every pinned sentence into its record, which keeps prose as the pinned statement of rules the code implements.
*Recommendation:* Option A.
*Owner choice:* Option A, as the corrected order already states ("the record's own file, or the driver or helper code that implements it"). No alarm is raised; the driver comments that cited the file by name cite the record instead, which puts AC-GATES, CL-D13, CL-D14, CL-D27, CL-D38, CL-D62, CL-D72 and CL-D100 into them, and `driver/review.js` and `driver/phases.js` gain CL-D11 and CL-D38 in a comment at a few bytes each; `driver/run.js` grows by nothing. A clause whose anchors fall in more than one file is split into one clause per file; the `closed-loop-issue/SKILL.md` halves of AC-GATES, CL-D13 and CL-D15 and the `autofix-addendum.md` half of CL-D92-prose keep their paths. Three clauses duplicated a pin another clause already held and are retired, with this record saying so: CL-D107-review-only (CL-D107-driver pins the relaunch), CL-D72-route-review-only (CL-D72-map-review and CL-D72-map-phases pin the two operations; the `harness_failed` line joins the former), and CL-D31-pr-boundary-pr (its two sentences were CL-D28's: one is retired below, the other is restated by the CL-D28 sentence the record pins). Four sentences were about the document or the prose path and are retired: the "Review-only is the default" heading (mode selection is SKILL.md's), "Issue workflow has no publication grant through this Skill", the arrow order block of CL-D62-pr (the derived-vocabulary surface Issue #110 keeps until the deletion), and CL-D24's narrowing of `DEC-EXT-SNAPSHOT-001`. The rule-stating tests assert the code or record instead; a test file holding both kinds keeps only its structural reads, which `test/issue-272-review-only-pins.test.js` names; the tests about the file's existence, headings, size, split, duplication guards, derived vocabulary surfaces, authority measurement and `contractInput` keep their reads until the deletion. The file is byte-identical and `driver/review.js` reads it into `contractInput` as before.
*Rationale:* The code is the one specification since CL-D111; a pin on it fails when the implementation changes, which a pin on prose no run reads as guidance cannot. A marker comment the alarms cannot hold is not worth a raise in a pull request that changes no behaviour: the record sentence pins the rule until a later change to that code earns the comment.
*Validity and invalidation conditions:* Applies to the clause pins and tests that named `references/review-only.md`. It changes no rule, grant or boundary: every requirement the file stated is either pinned to the code that enforces it, stated in its record, or retired as a sentence about the document. Four rules the file stated the packaged review-only driver does not implement; each is recorded here, not closed, and in its own record: the status block's `review_misses` line is always `none` (CL-D85), there is no SonarCloud path (CL-D17), `ABORTED` is never emitted (CL-D14), and a pasted status block is not a resume path, the driver resuming only a `WAITING_EXTERNAL_REVIEW` stop from its own run directory (CL-D13). The two other mode references, the deletion, `AUTHORITY_FILES`, both `CONTRACT_INPUT_FILES`, the guards and the ceiling are the later pull requests of #249. Reviving a pin on a deleted file, moving a rule out of its record without a code anchor, or closing one of the four gaps requires a new owner decision. #249 later deleted the file (CL-D119); `review.js` no longer hashes it into `contractInput`.
