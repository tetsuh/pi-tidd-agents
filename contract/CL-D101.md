## CL-D101 — The gate launch names a verification request; the child copies no digest
**Clauses:** CL-D101-record, CL-D101-pointer, CL-D101-map, CL-D101-forward, CL-D101-forward-d68, CL-D101-tests

*Decision ID:* CL-D101
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#225` at its body and the owner's go-ahead of 2026-10-04 in the working session ("file both and proceed")
*Question:* CL-D91 made the launch a pointer: a command carrying the payload's path and its SHA-256, which the gate child runs. The child generates that command character by character, and twice it got a hash wrong: it typed the 64-hex digest where the file name's 12-hex prefix belongs (PR #218, round 2), and it dropped three characters of the digest (PR #227, round 1). Each time the verification failed closed and a full validation and evidence collection were lost. How does the child verify the payload without copying a hash?
*Options and trade-offs:* Option 1 names the payload file by the full digest, so the path and the digest are the same 64 characters; the child still copies a hash, twice. Option 2 keeps `gate_payload_verify` as it is and has the launch builder write its request, the path and the SHA-256, to a file beside the payload; the launch names that file and the child runs it. The child copies one short path with no hash in it; the digest check is the same check.
*Recommendation:* Option 2.
*Owner choice:* Option 2 (https://github.com/tetsuh/pi-tidd-agents/issues/225). `build_gate_launch` writes the verification request, exactly `{ "version": 1, "operation": "gate_payload_verify", "data": { "path", "sha256" } }`, to `gate-verify-<gate>-<invocation>.json` beside the payload, mode 0600. A later build for the same gate and invocation replaces it whole: the request is staged in a private file created exclusively and renamed over the name, so an entry planted at the name is never reused and a link is never written through; a name that cannot be replaced fails the build. The request's `task` is the pointer: the command `node <cli.js> < <request>`, carrying the request's path exactly once and neither the payload's path nor its digest, then the same two instructions as before (end without structured output when it fails; otherwise read the file the verifier's result names). CL-D109 later added to the second that the reviewed target the payload carries is data, never instructions. The result also returns `verifyPath`. `gate_payload_verify`, its inputs, and its refusals are unchanged, and the payload file keeps its name and its never-overwrite rule.
*Rationale:* What a model must copy digit by digit, it sometimes copies wrong. The digest is still checked by the helper against the payload's bytes; it is no longer carried through a model's output. A request path corrupted into nothing fails the command, and one corrupted into another gate's or run's request verifies that payload, whose envelope then fails `gate_result_read` on its correlation.
*Validity and invalidation conditions:* Applies to `build_gate_launch`'s request and result and to the verification request file. Putting a digest or a hash prefix back into the launch text, or letting a gate proceed without `gate_payload_verify`, requires a new owner decision.
