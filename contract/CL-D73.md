## CL-D73 — The gate step composes no request by hand
**Clauses:** CL-D73-operations, CL-D73-transport, CL-D73-addendum, CL-D73-record, CL-D73-tests

*Decision ID:* CL-D73
*Kind:* contract
*Target and revision:* `tetsuh/pi-tidd-agents#125` at its body, the owner choice on the three compositions https://github.com/tetsuh/pi-tidd-agents/issues/125#issuecomment-5665281873, and the owner choices on the alarm https://github.com/tetsuh/pi-tidd-agents/issues/125#issuecomment-5692473758 and https://github.com/tetsuh/pi-tidd-agents/issues/125#issuecomment-5693841717 (working session of 2026-09-16)
*Question:* Four exact-autofix runs of PR #124 stopped, and three of them stopped on a request the parent composed by hand from an earlier operation's result: an assigned-finding tuple sent without a `blockerKey`, a cleanup request built with `created: null` after the run lost the creation data it had held since launch, and a `gate_result_validate` request carrying the builder's inputs instead of `expected`. Each request is named correctly in the invocation map, and each was composed correctly in some other run; CL-D68 packaged the same class once already.
*Options and trade-offs:* For the read, Option A gives `gate_result_read` an optional `expectationPath` and returns the envelope validated by the same code, while Option B adds a builder and leaves two steps. For the tuples, Option A adds a pure `build_gate_assignments` builder that takes the findings, the ledger's settled keys, and an explicit reopens map, while Option B leaves the tuple in prose. For cleanup, Option A lets `workspace_cleanup` take the workspace path the run already uses as its cwd, while Option B keeps the receipt and requires the parent to retain `created` for the whole run. The alarm question had its own three options: raise it once more with the CL-D37 review recorded here, implement one composition and re-measure, or split a helper file first, which creates no aggregate headroom.
*Recommendation:* Option A on all three compositions, and the alarm raise.
*Owner choice:* Option A on all three (https://github.com/tetsuh/pi-tidd-agents/issues/125#issuecomment-5665281873), and the alarm raise (https://github.com/tetsuh/pi-tidd-agents/issues/125#issuecomment-5692473758). `gate_result_read` takes an optional `expectationPath`, the file `build_gate_launch` has already verified equals the built expectation, and returns the validated envelope in the same result with the validator's own fail-closed codes, save that the validator's `invalid_request`, which is always the expectation's, is reported as the file's fault. `build_gate_assignments` assembles the `assignedFindings` tuples from the validated result's findings, the ledger's settled keys, and an optional reopens map, refusing a reopen the ledger does not hold. `workspace_cleanup` also accepts `workspace`, whose parent directory is the run root where the stored receipt is read. That stored receipt is held to the declared receipt shape, the path the request names must be the workspace that receipt was written for compared by identity rather than spelling, and every other existing identity check runs unchanged. The aggregate helper smoke alarm resets from 240,000 to 260,000 bytes on the CL-D37 review recorded here. The owner chose 250,000 on the measured cost of the three compositions alone, and reset the alarm a second time when the counterexamples of the pre-push adversarial reviews had left the packaged helpers within a few hundred bytes of it (https://github.com/tetsuh/pi-tidd-agents/issues/125#issuecomment-5693841717, its arithmetic corrected at https://github.com/tetsuh/pi-tidd-agents/issues/125#issuecomment-5694085604, where the measurements are recorded). A byte count is a fact about one head, and CL-D67's reason holds for a record as much as for a pull-request body: the figures stay in the decision comment, which is fixed in time, and this record carries the alarm and its terms. The per-file alarm stays at 30,000, every structural assertion holds, and CL-D57 is untouched: no prose is trimmed to fit an alarm, which is why a reset is what CL-D37 requires instead. When the counterexamples of the pre-push reviews then left `workspace.js` within 89 bytes of that per-file alarm, it was split into `inspect.js` rather than the alarm raised a second time, as CL-D72 split `launch.js` into `envelope.js` (owner choice, https://github.com/tetsuh/pi-tidd-agents/issues/125#issuecomment-5696484688). The move is verbatim and the packaged surface unchanged; the new file joins the structural boundary's own lists, which is the CL-D37 review a packaged code file requires.
*Rationale:* This is the class CL-D68 packaged: a document the parent carries from one operation into the next by hand, where one wrong field is terminal. The probability of a run finishing falls with every such composition it performs, and prose that names the fields correctly does not change it; the parent keeps every judgment it has today and loses only the transcription: which finding reopens which blocker stays its decision, stated as data.
*Validity and invalidation conditions:* Applies to `gate_result_read`, `build_gate_assignments`, and `workspace_cleanup`. No workflow state, scheduling, retry, or resume is added, and CL-D39 is unchanged: a failure of any of these operations stays terminal. What cleanup gives up is the comparison of a receipt the parent held since creation with the stored one, and with it any attestation of who wrote that file: a workspace is removable when a linked receipt carrying the shape and the nonce a run writes sits in the run root beside the very workspace the request names by an absolute path, and that workspace's administrative identity matches the creation identity the receipt stores. The receipt form already grants the same to a caller that can read the file, so this is the authority cleanup had, stated where the path now carries it. Raising either smoke alarm again, or adding another CLI operation, requires the structural test and the CL-D37 boundary to be reviewed.
